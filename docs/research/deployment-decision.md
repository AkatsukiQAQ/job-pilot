# Deployment decision

## Do we need a server
No, not for v1, and probably not for the first months of real use. Mita JobPilot is a single-user, read-only, light-CPU tool whose data fits in one SQLite file under 1 GB. Nothing about correctness requires 24x7 uptime: Gmail is durable (on wake, one history.list call with the saved historyId catches up everything that arrived while the PC was off; a 404 on a stale historyId just triggers a full resync), and job boards polled a few times a day merely go stale while the machine sleeps. The only two things a server buys are (a) reaching the UI from a phone/laptop while the main PC is off or asleep and (b) near-real-time alerts (interview invites, recruiter replies) while you are away from the PC. Neither exists as a need on day one.

Phase-by-phase: (1) Build/v1 (using it at the desk): run FastAPI + APScheduler + SQLite on the Windows 11 PC from a plain uv venv; no server, US$0, no ops. (2) First remote use (phone while the PC is awake): still no server; Tailscale Personal (US$0, no card) with `tailscale serve --bg 8000` gives an HTTPS origin on https://<pc>.<tailnet>.ts.net, which is required anyway because the browser microphone (getUserMedia) and PWA install only work in a secure context. The Gmail refresh token and email bodies never leave your house. The weak point is Windows sleep: both S3 sleep and Modern Standby (where the Desktop Activity Moderator freezes Win32 apps even though Wi-Fi stays up) stop the scheduler, so set `powercfg /change standby-timeout-ac 0` and run the app as a Windows service (WinSW) so it survives Windows Update reboots. (3) A server becomes worth it the moment you genuinely want sync to continue while the PC is off, or you find yourself leaving a ~60 W desktop on 24x7 just for Mita JobPilot: that electricity alone is roughly US$8-10/month at Japan's ~JPY 33/kWh, which is more than a US$5 Tokyo VPS (Vultr vc2-1c-1gb / Linode Nanode) or a Fly.io Machine (~US$4.33 in nrt), and comparable to the ~12-15-month payback of a ~US$180 Intel N100 mini PC that idles at 6-12 W. So the honest threshold is: 'I want it reachable/syncing when my PC is off' AND/OR 'I would otherwise keep the PC awake for it'. Below that, a server is pure overhead (patching, TLS, auth wall, backups, plus a third party holding your Gmail token).

Two myths to discard: 'the big clouds have a free always-on VM' (AWS accounts created after 2025-07-15 get a credits-based Free plan that closes after 6 months; Google's Always Free e2-micro is US-regions only; Azure's 750 h/month VMs end after 12 months) and 'serverless is free and simpler' (Cloud Run, Lambda, Vercel, Workers all have no persistent filesystem, so SQLite and the in-process scheduler must be re-architected around Turso/D1 plus an external cron, which is days of work for a one-user app). The only genuinely free always-on VM is Oracle Cloud Always Free (Ampere A1, now capped at 2 OCPU/12 GB after the 2026-06-15 halving, Tokyo/Osaka/Seoul home regions available), and it is best-effort: idle-reclaim rules that a light poller can trip, frequent 'out of host capacity' errors, and a card + phone at signup. Treat it as an opportunistic US$0 try, not a design dependency. The realistic paid answer is US$5/month, and the design decisions below make that move a config change rather than a rewrite.

## Recommended by phase
- Phase 0 — build and v1 (using it at the desk): Local Windows 11 PC: uv venv, `uvicorn` bound to 127.0.0.1, SQLite (WAL) on NTFS, APScheduler in-process; promote to a WinSW service once it is stable
  why: Zero cost, zero ops, best privacy, and nothing in the workload needs uptime. Gmail history.list makes sleep harmless (catch-up on wake), and job boards polled a few times a day just go stale. Spending this phase on hosting instead of on the parser/UI is the wrong trade.
- Phase 1 — first remote use (phone/laptop while the PC is awake): Same PC + Tailscale Personal with `tailscale serve --bg 8000` (HTTPS on https://<pc>.<tailnet>.ts.net); `powercfg /change standby-timeout-ac 0`; app and Tailscale both running as services
  why: Still US$0 and no card. Serve gives the secure context the mic and PWA install require, traffic is end-to-end WireGuard, and the Gmail token and email contents never leave home. The only cost is keeping the PC awake, which is also the natural test of whether you actually need Phase 2: if you find yourself leaving a 60 W desktop on overnight for this, that is US$8-10/month of electricity and the signal to move on.
- Phase 2 — sync must continue with the PC off, or you want access at any hour: US$5 Tokyo VPS (Vultr vc2-1c-1gb or Linode Nanode 1 GB; ConoHa 1GB if you are Japan-based) running the same Docker image or uv systemd service, reachable only over Tailscale, with nightly `VACUUM INTO` + rclone backups off-box. Privacy-first alternative at the same step: an Intel N100 mini PC at home (US$180-200 one-off) running the identical stack. Opportunistic US$0: spend 30 minutes trying Oracle Always Free A1 in ap-tokyo-1 first, sized 1 OCPU/2 GB, but do not depend on it
  why: A real VM with a persistent disk means SQLite and the in-process scheduler run unchanged (the ephemeral-filesystem problem is a PaaS issue, not a VPS one), Tokyo latency keeps the streaming chat snappy, and US$5 is cheaper than the desktop's electricity. Fly.io (~US$4.33 in nrt) is a fine substitute if you prefer `fly deploy` to managing Ubuntu, but its single-host volume with 5-day snapshot retention needs Litestream. Oracle is genuinely free but best-effort (halved allowance, idle reclaim, capacity errors), so it is a bonus, not a plan. Serverless re-architectures (Cloud Run/Modal/Workers + Turso/D1) cost days of rewriting to save US$5/month and hand the Gmail token to more parties; not worth it for one user.
- Phase 3 — optional growth (heavier parsing, embeddings, browser-only access): Same VPS scaled to the 2 GB tier (US$10-12), optionally with Cloudflare Tunnel + Access (or Caddy + your own auth) in front for browser-only phone access without the Tailscale app; Postgres only if a second writer or full-text/vector needs appear
  why: Because Phases 0-2 kept a single container image, a SQLAlchemy URL, env-based config and idempotent sync jobs, every step here is a config or size change, not a migration. Adding a login wall or a public hostname is safe because the auth middleware and proxy-header handling were built in Phase 0.

## Architecture implications
  - Twelve-factor config from the first commit: one pydantic-settings `Settings` with a JOBPILOT_ prefix (DATABASE_URL, DATA_DIR, HOST/PORT, BASE_URL, AUTH_MODE, TZ, LLM keys, Gmail client secrets path). No hardcoded Windows paths; the same image/venv runs on the PC, a VPS, Oracle ARM or a mini PC by changing env only.
  - One data directory (JOBPILOT_DATA_DIR) holds the SQLite file, the encrypted token store, attachments and backups. On a VPS/Fly/Railway this becomes the single mounted volume; on Windows it is an absolute path the SYSTEM service can reach.
  - Database access through SQLAlchemy (Core or ORM) with Alembic migrations and a URL of the form sqlite:///.../jobpilot.db. Enable WAL + busy_timeout via a connect hook. Avoid unwrapped SQLite-only features: use SQLAlchemy's JSON type, and if you adopt FTS5 for email search, isolate it behind a `search` module so Postgres tsvector or libSQL/Turso can replace it. Postgres/libSQL then becomes a URL + driver swap, not a rewrite.
  - Scheduler as thin glue, jobs as idempotent functions: APScheduler in-process for v1, but every sync (gmail_sync, jobboard_sync, cleanup) is a plain function also exposed as a CLI subcommand (`jobpilot sync gmail`). That lets systemd timers, Cloud Scheduler, GitHub Actions or a Modal cron drive it later with zero refactor. Persist cursors (Gmail historyId, job-board ETags/last-seen IDs) in the DB so runs are stateless and resumable; guard with a DB lock so an accidental second worker cannot double-poll.
  - Gmail integration built for interruption: gmail.readonly scope only; incremental sync via history.list from the saved historyId with a full-resync fallback on HTTP 404; if you add users.watch + Pub/Sub later, renew watch daily. Put the OAuth consent screen in 'In production' (unverified is fine for a single user) from day one, because 'Testing' status expires refresh tokens after 7 days and looks like a mysterious bug.
  - Secrets behind a TokenStore interface with pluggable backends: Fernet-encrypted file with the key from env (default, portable), Windows DPAPI (optional, local only), and later a cloud secret manager. Never write the refresh token in plaintext, never log it, and keep it out of git and SQLite.
  - Auth wall built in from Phase 0 even though v1 is localhost: JOBPILOT_AUTH_MODE=none|password|proxy (single-user password or passkey with a signed session cookie; 'proxy' trusts Cloudflare Access / Tailscale identity headers). Bind to 127.0.0.1 by default and only trust X-Forwarded-* from configured proxy IPs (uvicorn --proxy-headers --forwarded-allow-ips). Exposing the app via Tunnel or a public VPS then becomes a config change, never a scramble.
  - Assume HTTPS behind a reverse proxy: make BASE_URL configurable, serve the PWA manifest and icons from stable static paths, never rely on http:// origins (mic and install require a secure context). Use SSE for LLM streaming with a heartbeat every ~15 s so Cloudflare's 125 s timeout, Tailscale Serve, Caddy and nginx all pass it; avoid WebSockets unless you need bidirectional traffic.
  - Single-process assumption made explicit: one uvicorn worker, one SQLite writer, scheduler in that process. Document it and set workers=1 in the entrypoint; if you ever need multiple workers, move the scheduler to the CLI/timer path and switch DATABASE_URL to Postgres.
  - Ship a Dockerfile (python:3.12-slim, uv sync --frozen, non-root, /data volume, HEALTHCHECK on /healthz) and a compose file from week one, and build for linux/amd64 and linux/arm64 with buildx so Oracle A1, Raspberry Pi and Graviton stay open. Prefer pure-Python dependencies or ones with aarch64 wheels; keep Windows-only code (pywin32/DPAPI) in optional extras.
  - Backups are the exit strategy: a `jobpilot backup` command using SQLite's online backup API or `VACUUM INTO` to DATA_DIR/backups, a nightly schedule, and `jobpilot restore`. Test restore once. This is what makes Oracle's best-effort tier, Fly's single-host volume, or a dying mini PC acceptable risks.
  - Operational hygiene that costs nothing now: structured JSON logs to stdout only (no file-only logs), /healthz and /readyz endpoints, store all timestamps in UTC and render in JOBPILOT_TZ=Asia/Tokyo, and keep the UI a static SPA/PWA served from FastAPI's /static with a configurable API base so it could move to Cloudflare Pages if you ever go serverless.
  - Keep LLM calls stateless on the server side (API keys via env, no provider SDK state in the DB) so the chat layer is host-agnostic and the LLM bill stays independent of the hosting decision.
