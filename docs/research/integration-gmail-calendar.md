# Gmail (and Google Calendar) read-only ingestion for tracking job applications in a single-user local app (Mita JobPilot)

## Summary
Read-only Gmail ingestion for one personal Google account is fully feasible with the Gmail API and the restricted scope https://www.googleapis.com/auth/gmail.readonly, using a "Desktop app" OAuth client and google-auth-oauthlib's InstalledAppFlow.run_local_server; no Google verification or CASA assessment is required because Google's official exceptions list "Personal use: if you are the only user of your app" as exempt. The one real friction point is token lifetime: while the consent screen (Google Auth Platform > Audience) is External + "Testing", Google's docs state that test-user authorizations and refresh tokens expire 7 days after consent (unless only name/email/profile scopes are requested), so a Testing-status app forces a browser re-consent every week; the documented fix is to click "Publish app" (In production) and skip verification, after which the user clicks through the "Google hasn't verified this app" screen once, an unverified-app cap of 100 total users applies (irrelevant for one user), and the refresh token then only dies if unused for 6 months, revoked, or the Gmail password is changed. "Internal" user type is not available to a personal @gmail.com account: Google says an organization resource "is available for Google Workspace and Cloud Identity customers". Full verification would cost roughly USD 675–855/year via TAC Security (Google's discounted CASA Tier 2 partner) or 800–1,500+ at other labs plus several weeks of review, and annual re-assessment; it is unnecessary for personal use. Alternatives: IMAP (imap.gmail.com:993) with a 16-character App Password still works in 2026 for personal accounts with 2-Step Verification (Google discourages but has not deprecated it), but an App Password is a full-mailbox credential with no scope enforcement so read-only becomes a discipline of your code; Google Takeout MBOX is manual (7-day link, 5 downloads, at best every-2-months scheduling) and the Data Portability API does not cover Gmail, so Takeout is only useful for a one-time historical backfill; open-source read-only Gmail MCP servers exist (Maheidem/gmail-mcp, zayansalman/gmail-attachments-mcp, ArtyMcLabin fork with --scopes=gmail.readonly) but still need your own OAuth client and add nothing for a sync pipeline. For near-real-time tracking, polling users.history.list every 60–120 s (2 quota units per call) is trivially within quota (6,000 units/min/user, 1.2M/min/project) and needs no cloud infra; users.watch + Cloud Pub/Sub (pull subscription, free under 10 GiB/month, watch must be renewed at least every 7 days) is a v2 optimization, not a v1 need. Google Calendar with calendar.events.readonly (sensitive, not restricted) plus events.list syncToken incremental sync gives interview events with attendees, organizer and Meet/conference URIs. Parsing: ATS/platform template mail (Greenhouse no-reply@us.greenhouse-mail.io, Lever no-reply@hire.lever.co, Ashby no-reply@ashbyhq.com, Workday <tenant>@myworkday.com, Indeed indeedapply@indeed.com, HackerRank no-reply@hackerrank.com, HireVue interviews@hirevue.com, Calendly notifications@calendly.com, Google Calendar Sender: calendar-notification@google.com) is reliably detectable with sender-domain and subject rules; free-form recruiter mail, Japanese keigo (面接のご案内 vs お祈りメール) and Chinese notices, plus extraction of company/role/stage/dates, need an LLM classifier with structured output. All read-only scopes listed below cannot send, draft, label, modify or delete: those operations require gmail.send/compose/modify/labels or mail.google.com, and the API rejects them with 403 insufficient scopes.

## Hard constraints
  - gmail.readonly is a Google RESTRICTED scope (same class as gmail.modify and mail.google.com); gmail.metadata is also restricted; only gmail.labels and the add-on scopes are non-sensitive.
  - External + Testing publishing status: refresh tokens and test-user consents expire 7 days after consent unless the only scopes are name/email/profile (openid, userinfo.email, userinfo.profile). Weekly re-consent is unavoidable in Testing.
  - Publishing status In production (even unverified) lifts the 7-day expiry; the refresh token then expires only if unused 6 months, revoked, Gmail password changed (Gmail-scope tokens), >100 live refresh tokens per client ID, or time-based access expired.
  - Unverified apps requesting sensitive/restricted scopes get a hard cap of 100 new users total after the unverified screen is first shown.
  - 'Internal' user type requires the project to belong to a Google Cloud Organization; Google: 'An organization resource is available for Google Workspace and Cloud Identity customers.' A personal @gmail.com account cannot use Internal.
  - Verification is officially NOT required for personal use ('if you are the only user of your app or if your app is used by only a few users, all of whom are known personally to you') or while in Testing.
  - If verification is ever pursued: restricted scopes need brand verification + restricted-scope review + CASA security assessment repeated at least every 12 months; self-scan tier no longer exists; cheapest lab quote USD 675/app/year (TAC Security Basic).
  - messages.list q= (Gmail search syntax) cannot be used with the gmail.metadata scope; use gmail.readonly.
  - history.list startHistoryId is 'typically valid for at least a week, but in some rare circumstances may be valid for only a few hours'; on HTTP 404 you must full-resync.
  - users.watch must be re-called at least every 7 days (Google recommends daily); notifications contain only emailAddress and historyId.
  - Gmail API quota (current doc): 1,200,000 quota units/min/project; 6,000 quota units/min/user/project; 80,000,000 units/day/project before charges. Unit costs: messages.list 5, messages.get 20, messages.attachments.get 20, threads.list 10, threads.get 40, history.list 2, labels.list 1, getProfile 1, watch 100.
  - Calendar API quota: 10,000 requests/min/project, 600 requests/min/user, 1,000,000/day/project free threshold. Calendar scopes are 'sensitive' (verification without CASA) but exempt for personal use exactly like Gmail.
  - Calendar events.list with syncToken cannot be combined with iCalUID, orderBy, privateExtendedProperty, q, sharedExtendedProperty, timeMin, timeMax, updatedMin; a 410 GONE means wipe local store and full-sync.
  - IMAP via SASL XOAUTH2 requires the full https://mail.google.com/ scope (read/compose/send/delete) - NOT read-only; the only read-only-compatible IMAP path is an App Password with client-side discipline (EXAMINE + BODY.PEEK).
  - App Passwords require 2-Step Verification, are unavailable with Advanced Protection or security-key-only 2SV or admin-disabled Workspace accounts; basic-password IMAP/SMTP/POP is dead for all accounts since 1 May 2025 (personal accounts lost the LSA toggle 30 May 2022).
  - Google Takeout cannot be automated for Gmail: the Data Portability API covers Chrome, Maps, Play, Search, Shopping, YouTube, My Activity etc., not Mail or Calendar.
  - For a Desktop app client the client_secret is not treated as a secret; use loopback redirect http://127.0.0.1:<port> and PKCE (recommended by Google).
  - Read-only scopes cannot write: users.messages.send/insert/import require gmail.send/insert/compose/modify/mail.google.com; drafts.* require gmail.compose/modify/mail.google.com; messages.modify/batchModify/trash/delete and labels.create/update require gmail.modify or gmail.labels or mail.google.com; calendar.readonly / calendar.events.readonly cannot insert/patch/delete events.

## Recommendation
v1 (one user, local Windows app): Option B. Create one GCP project 'jobpilot', enable Gmail API + Google Calendar API, configure Google Auth Platform with user type External, add yourself as test user, request exactly two scopes: https://www.googleapis.com/auth/gmail.readonly and https://www.googleapis.com/auth/calendar.events.readonly (add calendar.calendarlist.readonly only if you need multiple calendars). Create a 'Desktop app' OAuth client; put credentials.json and token.json under %LOCALAPPDATA%\\Mita JobPilot\\secrets (gitignored). Build the auth flow with google-auth-oauthlib InstalledAppFlow.run_local_server(port=0) and PKCE. First run it in Testing to confirm scopes work; then click 'Publish app' (do not submit for verification), delete token.json, and re-consent through the 'Google hasn't verified this app' > Advanced screen so the new refresh token is not on the 7-day clock. Implement a 'token health' check on startup that detects invalid_grant and re-launches the browser flow (this is the fallback cadence if you ever choose to stay in Testing: re-consent weekly). Sync design: (1) initial backfill via users.messages.list with q='newer_than:180d -category:promotions -category:social' pages of 500, then messages.get format=metadata with metadataHeaders=[From,To,Reply-To,Sender,Subject,Date,Message-ID,In-Reply-To,References,List-Unsubscribe,X-Google-Calendar-Notification] for everything and format=full only for messages that pass the job-related gate; store the max historyId; (2) incremental: every 60–120 s call users.history.list(startHistoryId, historyTypes=[messageAdded,labelAdded], labelId optional) and fetch new message IDs; on 404 rerun backfill from the newest stored internalDate. This is ~3,000 quota units/day, i.e. negligible. Skip users.watch/Pub/Sub until v2. Calendar: initial events.list(calendarId='primary', timeMin=now-90d, singleEvents=true, orderBy=startTime, maxResults=2500), save nextSyncToken, then events.list(syncToken=...) on the same 1–2 min tick; join events to applications by attendee/organizer domain, summary keywords (interview|面接|面談|面试|screen|onsite|loop), and conferenceData.entryPoints uri (meet.google.com, zoom.us, teams.microsoft.com) or Calendly-created events. Classification: two stages. Stage 1 deterministic gate + coarse label from sender domain/subject regex table (below) with a stored 'rule_id'; Stage 2 send only gated-in or ambiguous messages (headers + first ~4k chars of text/plain, HTML stripped) to Claude/GPT with a JSON schema {is_job_related, category, company, role, ats, stage, action_required, deadline_iso, event_start_iso, links[], language, confidence}. Cache LLM results by Gmail message id so nothing is re-classified. Storage: SQLite via sqlite3 or SQLAlchemy with the tables listed in concrete_details. Write nothing back to Google: no labels, no read-state changes (the Gmail API never marks read on get; if you ever fall back to IMAP use BODY.PEEK). Defer to v2+: users.watch + Pub/Sub pull for sub-second updates; attachment ingestion (messages.attachments.get, 20 units) for offer PDFs; full verification only if Mita JobPilot is ever shared; IMAP/App Password only as an emergency fallback if OAuth tokens keep dying; Takeout MBOX import only as an optional one-time historical backfill/offline classifier training set.

## Options
### A. Gmail API + OAuth Desktop client, gmail.readonly, consent screen left in Testing [read_only_ok=True, cost=USD 0 (Gmail API free under 80M quota units/day/project), effort=hours, risk=none]
Create a GCP project, enable Gmail API (and Calendar API), configure Google Auth Platform: user type External, publishing status Testing, add your own Gmail address as the single test user, create a 'Desktop app' OAuth client, download credentials.json. Use google-api-python-client + google-auth-oauthlib InstalledAppFlow.from_client_secrets_file(...).run_local_server(port=0); store token.json locally. Poll users.history.list for changes.
Pros:
  - Zero verification, zero cost, works today
  - True least privilege: scope enforced server-side by Google; app literally cannot send/label/delete
  - No 'unverified app' scary screen (only a 'tester' warning)
  - Full Gmail search syntax via messages.list q= and body access via messages.get format=full
Cons:
  - Refresh token and consent expire 7 days after consent (Google: 'Authorizations by a test user will expire seven days from the time of consent') -> weekly browser re-consent
  - Test user cap 100 (irrelevant for one user)
  - Restricted scope: if you ever add users you must verify + CASA
### B. Same as A but publish consent screen to 'In production' WITHOUT submitting for verification (recommended v1) [read_only_ok=True, cost=USD 0, effort=hours, risk=low]
Identical setup, then click 'Publish app' on the Audience page and do not submit the verification form. On first consent you see 'Google hasn't verified this app' and click Advanced > Go to <app> (unsafe). Google's own exceptions list says verification is not required 'if you are the only user of your app'. Re-run the OAuth flow AFTER publishing so the new refresh token is not on the 7-day clock.
Pros:
  - Refresh token no longer expires weekly; only revoked if unused 6 months, user revokes, Gmail password change, or >100 live refresh tokens per client
  - Still exempt from verification and CASA (personal use)
  - Same enforced read-only scope as A
Cons:
  - Unverified-app warning screen on each (rare) re-consent
  - Hard cap: 100 new users total once unverified screen is shown (irrelevant for one user)
  - Google's Audience page wording ('may be subject to verification ... before it may request authorization of sensitive or restricted scopes') is ambiguous; behaviour confirmed by Google's personal-use FAQ text and many developer reports, but verify empirically on day one
### C. Full OAuth verification + CASA security assessment (restricted scope) [read_only_ok=True, cost=USD ~675–1,500 per year plus weeks of paperwork, effort=weeks, risk=none]
Submit brand verification (privacy policy URL, homepage, domain verification, scope justification, demo video) then restricted-scope review and an annual CASA assessment (AL1/AL2, formerly Tier 2/3) by an App Defense Alliance lab.
Pros:
  - Removes unverified screen and 100-user cap; required only if the app is ever distributed
Cons:
  - Costs USD 675–855/yr (TAC Security Basic/Premium, Google's discounted partner) or 800–1,500+ elsewhere; Tier 3 USD 4,500+
  - Several weeks; must re-verify and re-assess every 12 months
  - Requires public homepage + privacy policy; pointless for a one-user local app
### D. IMAP (imap.gmail.com:993 SSL) with a Google App Password [read_only_ok=True, cost=USD 0, effort=hours, risk=low]
Turn on 2-Step Verification, create a 16-char App Password at https://myaccount.google.com/apppasswords, connect with Python imaplib (or imapclient) to imap.gmail.com:993, SELECT '[Gmail]/All Mail' with EXAMINE (read-only), search with Gmail's X-GM-RAW extension, fetch with BODY.PEEK[] so \Seen is never set, and use X-GM-MSGID/X-GM-THRID/X-GM-LABELS for stable IDs.
Pros:
  - No GCP project, no consent screen, no 7-day expiry
  - Google confirms App Passwords still work in 2026 (LSA/basic-password shutdown 'with the exception of app passwords')
  - Simple, standard protocol; works with Takeout MBOX code paths
Cons:
  - App Password is a full-account credential: can SMTP-send, STORE flags, EXPUNGE; read-only is only as good as your code (use EXAMINE + BODY.PEEK)
  - Google: 'App passwords aren't recommended and are unnecessary in most cases'; unavailable if account uses Advanced Protection, security-key-only 2SV, or is a Workspace account whose admin disabled them
  - IMAP sessions last ~24 h; no historyId-style change feed (must poll UID ranges/IDLE); Gmail IMAP bandwidth limits apply
  - No Calendar access via this path
### E. Google Takeout MBOX export (one-time backfill only) [read_only_ok=True, cost=USD 0, effort=hours, risk=none]
takeout.google.com > Mail > MBOX (labels preserved in X-Gmail-Labels header), optional Calendar ICS; parse with Python mailbox.mbox. Can be scheduled 'every 2 months for one year'; download link valid ~7 days, 5 downloads per archive.
Pros:
  - No API credentials at all; gives full history for building/evaluating the classifier offline
  - Also exports Calendar as ICS
Cons:
  - Manual, slow (hours to days), not near-real-time
  - Data Portability API does NOT include Gmail/Calendar, so it cannot be automated
  - Archive size up to 50 GB; MBOX from a large mailbox is heavy
### F. Reuse an open-source read-only Gmail MCP server [read_only_ok=True, cost=USD 0, effort=hours, risk=none]
Maheidem/gmail-mcp (Python, `uvx mcp-gmail-reader`, gmail.readonly only), zayansalman/gmail-attachments-mcp (3 tools, gmail.readonly), or ArtyMcLabin/Gmail-MCP-Server (Node; `auth --scopes=gmail.readonly`; MCP readOnlyHint annotations). GongRzhe/Gmail-MCP-Server (1.1k stars) was archived 2026-03-03.
Pros:
  - Drop-in tools for the chat agent (Claude/GPT tool use) to search/read mail on demand
  - Reference implementations of the OAuth flow
Cons:
  - Still require your own GCP OAuth client -> same Testing/production decision as A/B
  - Designed for ad-hoc queries, not an incremental sync pipeline; no historyId tracking, no DB
  - Some forks default to gmail.modify; must pin scopes explicitly
### G. Add-on for v2: users.watch + Cloud Pub/Sub pull subscription [read_only_ok=True, cost=USD 0 under free tier, effort=days, risk=none]
Create Pub/Sub topic, grant roles/pubsub.publisher to gmail-api-push@system.gserviceaccount.com, call users.watch {topicName, labelIds:['INBOX'], labelFilterBehavior:'INCLUDE'} daily (must be at least every 7 days), consume with a Pub/Sub PULL subscription from the local app (no public HTTPS endpoint needed), then call history.list from the stored historyId.
Pros:
  - Sub-second change notification (max 1 event/s/user)
  - Pub/Sub free tier: first 10 GiB/month; a personal inbox is far under that
  - Notification carries only {emailAddress, historyId}, no content leaves Google
Cons:
  - More moving parts (Pub/Sub client, IAM, daily watch renewal cron)
  - May require enabling billing on the project (open question)
  - Polling history.list every minute already achieves 'near-real-time' for a job-tracker

## Concrete details
  - Python packages: google-api-python-client, google-auth-httplib2, google-auth-oauthlib (Gmail quickstart); optional google-cloud-pubsub for v2 push; imapclient or stdlib imaplib for IMAP fallback; stdlib mailbox for Takeout MBOX.
  - OAuth: client type 'Desktop app'; InstalledAppFlow.from_client_secrets_file('credentials.json', SCOPES).run_local_server(port=0); loopback redirect http://127.0.0.1:<port>; PKCE recommended; refresh with creds.refresh(Request()); token.json contains refresh_token; per-client limit 100 live refresh tokens per Google account.

## Open questions
  - Empirically confirm on day one that 'Publish app' to In production with gmail.readonly (restricted) lets the project owner click through the unverified-app screen without a verification submission; Google's Audience page wording is ambiguous, though Google's personal-use FAQ and many developer reports say it works. Fallback: stay in Testing and re-consent weekly.
  - Which mailbox will be read: a personal @gmail.com account or an employer Google Workspace account? Workspace tenants can block 'unconfigured third-party apps' by default and admins can disable App Passwords; also reading an employer mailbox for job hunting is a policy/ethics risk. Assume personal Gmail.
  - Does the account use passkeys-only/'skip password' sign-in, security-key-only 2SV, or Advanced Protection? If so the App Password fallback (Option D) is unavailable.
  - Does enabling Pub/Sub (v2 push) require linking a billing account to the project? Free tier covers usage, but API enablement may still need billing; verify before choosing push over polling.
  - The Gmail quota page currently states 6,000 quota units/min/user/project and messages.get = 20 units; older docs cited 250 units/s/user and messages.get = 5. Confirm actual enforcement in Cloud Console Quotas after first backfill and tune batch sizes.
  - LinkedIn's exact job-status sender addresses (jobs-noreply@linkedin.com, inmail-hit-reply@linkedin.com) are not published in LinkedIn Help; verify against your own inbox headers (DKIM d=linkedin.com) before hard-coding.
  - Exact scout-notification sender addresses for Bizreach (beyond @bizreach.co.jp) and Wantedly (beyond @wantedly.com domain), and for Chinese platforms (zhipin.com/zhaopin.com/liepin.com/lagou.com), need sampling from the real inbox; many of these platforms deliver primarily in-app.
  - How much history to backfill (90/180/365 days) and whether to fetch format=full bodies for everything or only gate-passed mail (cost: 20 units and LLM tokens each).
  - Which LLM (Claude vs GPT) runs the classifier locally, its per-message cost at ~4k input tokens, and whether to run a small local model for the gate to keep restricted-scope data off third-party servers (Google's CASA trigger is 'ability to access data from or through a third-party server'; irrelevant for exempt personal use but relevant to your own privacy posture).
  - Calendar: single 'primary' calendar or multiple (work + personal)? Multiple calendars need calendar.calendarlist.readonly and one syncToken per calendarId.
