> **AI 调研附录**（生成于 2026-09-16，英文）。内容由并行调研 agent 对照官方页面整理，verified/unverified 标注以原文为准；实现前需再次核对。相关更正见 japan-critique.md 与 proposal-judgments.md。

# Proposal P1 (data): Data-model-and-memory-first. The product is one local SQLite ledger with explicit provenance and bi-temporal memory: raw observations from the outside world are appended immutably as source_items, everything the user believes or decides lives in separate user-state tables, and every automated derivation between the two is stamped with (source_item_id, extraction_run_id, actor, before/after) and routed through precedence rules that decide auto-apply vs. pending confirmation. Gmail, Google Calendar, the LinkedIn archive and public job boards are pluggable pull-only Sources; CLI, MCP server (Claude Desktop / Claude Code / Codex) and a later web UI are interchangeable Views over the same core services. Tracker, chat, memory and search ranking all hang off the same entities, so the loop (profile + outcomes -> ranking -> interactions -> profile) is a set of tables, not a feature.
Mita JobPilot is a single-user, local-first SQLite ledger (companies, job postings, applications, events, interviews, typed bi-temporal profile facts) fed only by pull-only read-only sources (Gmail/Calendar API read-only scopes, LinkedIn data-archive files, public ATS/job-board endpoints) through a rules-then-LLM extraction pipeline whose every automated change is provenance-stamped and either auto-applied under strict precedence rules or parked as a pending_action for the user to confirm; Claude/GPT chat and voice are views that call the same core services through an MCP server first and a web UI later, and job search ranks new postings against the same profile memory and outcome ledger so recommendations improve as applications resolve.

## Architecture components
- Store (jobpilot.db): Single SQLite file holding all five memory layers (ledger, profile facts, episodic, semantic index, behavioural signals) plus provenance tables (source_item, extraction_run, pending_action, audit_log). Owns schema, migrations, PRAGMAs, FTS5 and (v1.5) sqlite-vec virtual tables. Location %LOCALAPPDATA%\JobPilot\jobpilot.db (platformdirs.user_data_dir('Mita JobPilot')), gitignored. [stdlib sqlite3 (SQLite 3.50.4 verified: FTS5 + enable_load_extension available in the uv-managed CPython 3.12.12); WAL, foreign_keys=ON, busy_timeout=5000; hand-written numbered SQL migrations (src/jobpilot/db/migrations/NNN_*.sql) applied by a 60-line runner recording schema_migrations; Pydantic v2 row models; sqlite-vec 0.1.9 from v1.5; connection factory isolated so sqlite3 -> sqlcipher3 is a one-function swap in v2.]
- Core services (jobpilot.core): The only code allowed to write to the DB. ledger (companies/jobs/applications/events + derive_status + match_application), schedule (interview_event/pending_schedule), proposals (pending_action lifecycle, confirm/apply, audit_log diffs), memory (profile_fact CRUD with supersession, profile_snapshot hashing, prompt-block rendering, episode summaries, retrieval), classify (rule table + LLM structured-output classifier with extraction_run cache), search (dedup, features, hard filters, soft score, LLM rerank, search_run bookkeeping). Every public function takes an Actor ('user'|'rule'|'llm'|'import'|'system') and writes audit_log. [Pure Python 3.12, Pydantic v2 models, rapidfuzz for fuzzy matching, python-dateutil, unicodedata.normalize('NFKC'). No network imports allowed in this package (enforced by a test).]
- Sources (jobpilot.sources): Pull-only connectors implementing a Source protocol with exactly three methods: backfill() -> Iterable[RawItem], pull_incremental(cursor) -> (Iterable[RawItem], new_cursor), describe(). They produce RawItem(source_kind, external_id, external_thread_id, occurred_at, headers, body_text, payload) and never touch the ledger; the ingest service upserts them into source_item. Sources: gmail (gmail.readonly), gcal (calendar.events.readonly), linkedin_archive (ZIP/CSV parser, zero network), ats boards (Greenhouse, Lever, Ashby, SmartRecruiters, Workable, Recruitee, Teamtailor RSS, Rippling), sitemaps (TokyoDev, Japan Dev + JSON-LD), aggregators (Adzuna, JSearch). [google-api-python-client 2.200 + google-auth-oauthlib 1.4.1 wrapped in ReadOnlyGmail/ReadOnlyCalendar facades exposing only list/get/history/profile; httpx via a GetOnlyClient subclass that raises on non-GET/HEAD; feedparser, extruct, selectolax, protego for robots.txt; zipfile + csv (utf-8-sig, newline='') for LinkedIn.]
- LLM adapters (jobpilot.llm): Provider-switchable structured extraction and reranking (email classification, application-event extraction, profile-fact extraction, job judgement) plus PII aliasing before any text leaves the machine and cost/usage logging into extraction_run. Chat itself is NOT here until Phase 5; in Phase 3 chat runs in external MCP hosts. [anthropic 1.6 (client.messages.parse(model='claude-opus-5', output_config={'effort':'low'}, output_format=PydanticModel), adaptive thinking default, check stop_reason=='refusal'); openai 3.14 (client.responses.parse(model=cfg.openai_model, text_format=PydanticModel)); model IDs only from settings; Phase 5 adds pydantic-ai 2.43 (pydantic-ai-slim[anthropic,openai,mcp]) for the chat Agent with requires_approval tools.]
- Views: CLI (jobpilot.cli): First and always-available view. Commands: company/job/app add|show|list, app status|log|note, pipeline, calendar, inbox (review pending_actions), confirm/deny, remember, profile, forget, import linkedin <zip>, gmail auth|backfill|sync, search, watch add, db upgrade, doctor (prints scopes in token, DB stats). [typer + rich tables; console script [project.scripts] jobpilot = 'jobpilot.cli:main'.]
- Views: MCP server (jobpilot.views.mcp_server): Exposes read tools (search_applications, get_application, list_pipeline, upcoming_interviews, search_memory, get_profile, search_jobs, explain_fit, get_sync_status) and two-phase mutation tools (propose_status_update, propose_event, propose_memory_fact, propose_note, propose_job_interaction, confirm_action, cancel_action, list_pending_actions) over stdio. Registered in Claude Desktop, Claude Code and Codex so Claude-vs-GPT switching and voice come from the host in Phase 3. [official mcp 2.2.0 Python SDK (FastMCP-style decorators; 2.x is a major rework, verify import paths against the 2.x docs), console script jobpilot-mcp; deterministic tools/list order; readOnlyHint annotations on read tools.]
- Views: Web UI (Phase 5): Pipeline board, application detail with linked emails/events, interview calendar (month + agenda, JST), job workbench (filter/sort/compare up to 3), memory inbox with confirm cards, chat panel with provider dropdown, push-to-talk mic, SSE live updates. [FastAPI 0.141 + uvicorn on 127.0.0.1:8765, sse-starlette 3.4; React 19 + TypeScript + Vite 8 + TanStack Query 5 + Tailwind 4 in frontend/ (fallback: NiceGUI 3.16 mounted via ui.run_with(app) if the JS toolchain slows you down); Web Speech API push-to-talk in Chrome/Edge; pydantic-ai Agent with DeferredToolRequests for confirm cards.]
- Scheduler + event bus: In-process periodic jobs: gmail_incremental_sync (history.list) every 90 s, gcal_sync (syncToken) every 120 s, watch_target polls every 2-6 h with per-source token buckets, daily sitemap diff, nightly housekeeping (expire facts, decay learned weights, purge old body_text, mark ghosted candidates). Publishes progress to an asyncio broadcaster consumed by SSE. Phase 1-2 run these via explicit CLI commands (jobpilot sync); the scheduler arrives with the long-running process in Phase 2b/5. [APScheduler 3.11.3 AsyncIOScheduler inside a FastAPI lifespan (or a plain `jobpilot daemon` asyncio loop before the web app exists); APScheduler 4 avoided (alpha).]
- Secrets: API keys (Anthropic, OpenAI, Adzuna, JSearch) in Windows Credential Manager; Google OAuth token JSON and future SQLCipher key as DPAPI-encrypted files (Credential Manager blob limit is too small for token JSON). Startup token-health check refuses to run if token scopes are not a subset of the read-only allowlist. [keyring 25.7 (WinVaultKeyring) for short strings; pywin32 win32crypt.CryptProtectData/CryptUnprotectData for %LOCALAPPDATA%\JobPilot\google_token.dpapi; SecretStore Protocol with EnvSecretStore for tests.]
- Guarantee test suite (tests/test_readonly_guarantee.py + tests/test_memory_semantics.py): Executable version of the design rules: requested OAuth scopes == {gmail.readonly, calendar.events.readonly}; no forbidden method names in sources/; ruff banned-api forbids smtplib/imaplib/googleapiclient writes; every registered tool declares side_effect in {'none','local_db'}; core never imports network libs; precedence matrix and supersession semantics covered by fixtures. [pytest + anyio; ruff 0.16 with [tool.ruff.lint.flake8-tidy-imports.banned-api]; pyright standard mode.]

## Data flow
INGEST: Source.pull_incremental(cursor) -> RawItem -> ingest.upsert_source_item (UNIQUE(source_kind, external_id); content_hash; body_text stored, purgeable) -> classify.rules (sender-domain + subject regex table, precision-tracked rule_id) -> if gated-in or ambiguous: classify.llm (PII-aliased headers + first ~4k chars -> structured MemoryExtraction/EmailClassification; cached by extraction_run UNIQUE(source_type, source_ref, prompt_version, schema_version)) -> candidates (ApplicationEventCandidate, FactCandidate, InterviewCandidate, JobPostingCandidate) -> proposals.route(candidate, actor, confidence, existing_row) applies the precedence matrix: AUTO-APPLY (rule precision>=0.95 events; LLM events with confidence>=0.85 and an unambiguous application match; application.status recomputed by derive_status() only while status_set_by='auto'; job_posting fact refresh from the same source) or PENDING (everything touching user-set rows, all profile facts except explicit first-person high-confidence statements, ambiguous application matches which carry a candidate list, new-application creation, interview times parsed from prose) -> pending_action rows reviewed via CLI `inbox`, MCP confirm_action, or web confirm cards -> apply writes ledger/profile rows with source_item_id + extraction_run_id + actor and one audit_log row (before_json/after_json) per mutation. Calendar: gcal events -> source_item -> interview_event (status confirmed only when start time comes from the Calendar API or an explicit confirmation email; meeting_url only when a conference URI exists, otherwise NULL rendered as 'meeting link pending') linked to application by attendee domain/company_alias/thread. LinkedIn: ZIP -> source_import -> source_item per CSV row -> applications/saved jobs/preferences upserted by natural keys, Job Seeker Preferences become profile_fact candidates. SEARCH LOOP: watch_target polls + aggregator queries + Gmail job-alert mails -> job_posting (UNIQUE(source_kind, source_id); canonical_key sha1(company_norm|title_norm|country|city_or_remote); job_sighting per poll; is_active after 3 misses) -> exclude anything with job_interaction in (dismissed, applied, withdrawn) or an application -> hard filters from active profile_facts with polarity hard_require/hard_exclude (SQL) -> job_feature vector -> soft score with preference_weight (0.7 stated + 0.3 learned) -> top 20-30 to LLM rerank with the rendered profile block, recent outcome summary from fit_signal, and dismissal reasons from job_interaction.reason_text -> job_judgement rows keyed by (job_id, profile_snapshot_hash, prompt_version) -> search_run/search_run_result -> shown -> user actions logged in job_interaction -> outcomes (application.outcome, rejection/offer events) written to fit_signal -> nightly weight update (v2) and 'outcome_inferred' profile_fact candidates ('you dismissed 5 consulting roles: add company_type_pref avoid consulting?') back into the memory inbox. CHAT: Phase 3 host (Claude Desktop/Claude Code/Codex) -> MCP tools -> core services; the model records facts via propose_memory_fact. Phase 5 own UI -> pydantic-ai Agent -> same core functions as tools; every turn persisted to chat_turn; background extraction after each user turn produces candidates; approvals resume the run with DeferredToolResults. All timestamps stored UTC ISO-8601, rendered Asia/Tokyo.

## Data model
- source_import: import_id INTEGER PK, source_kind TEXT, label TEXT (zip filename | 'gmail_backfill' | 'gmail_history' | 'gcal_sync' | watch_target identifier), sha256 TEXT NULL, started_at, finished_at TEXT (UTC ISO), n_items INTEGER, status TEXT CHECK IN ('running','ok','failed'), error TEXT
  Batch-level provenance. Every source_item points at exactly one import, so 'LinkedIn data as of <archive_date>' and 'last Gmail sync' are queries, not flags. Raw LinkedIn ZIPs are copied to data/raw/linkedin/<archive_date>/ before parsing.
- source_item: item_id INTEGER PK, source_kind TEXT CHECK IN ('gmail_message','gcal_event','linkedin_csv_row','ats_board_json','aggregator_json','sitemap_page','manual','chat_turn'), external_id TEXT (Gmail message id | Calendar event id | sha1(csv file stem|row) | ATS job id | URL), external_thread_id TEXT (Gmail threadId | Calendar iCalUID | conversation id), import_id FK, observed_at, occurred_at TEXT, content_hash CHAR(64), headers_json TEXT (From, To, Subject, Date, Message-ID, In-Reply-To, References, List-Unsubscribe, Authentication-Results, X-Google-Calendar-Notification), body_text TEXT NULL (purgeable), payload_json TEXT (full API/CSV payload), classification TEXT CHECK IN ('job_related','not_job','unknown'), classifier TEXT CHECK IN ('rule','llm','user'), rule_id TEXT NULL, class_json TEXT (is_job_related, category, company, role, ats, stage, action_required, deadline_iso, event_start_iso, links, language, confidence), processed_at TEXT, linked_application_id FK NULL, linked_job_id FK NULL, UNIQUE(source_kind, external_id)
  The immutable observation layer. Append-only; never edited except classification/link columns and body purge. Because raw payloads are kept, every derived row (events, facts, postings) can be re-derived after a prompt or rule change. Nightly job NULLs body_text older than 90 days once a derived application_event exists. Email categories: confirmation, viewed, rejection, interview_invite, scheduling_request, assessment, offer, outreach, job_alert, calendar, system, other.
- sync_state: source_key TEXT PK ('gmail' | 'gcal:primary' | 'watch:<watch_target_id>'), cursor TEXT (Gmail historyId | Calendar nextSyncToken | ETag/Last-Modified), last_success_at, last_error TEXT, extra_json TEXT
  Gmail: on HTTP 404 from history.list re-run backfill from newest stored internal_date and reset cursor. Calendar: on 410 GONE wipe local gcal source_items' link and full-sync.
- company: company_id INTEGER PK, name TEXT, name_norm TEXT UNIQUE (NFKC, casefold, legal suffixes stripped: 株式会社, (株), 合同会社, Inc, Ltd, K.K., GmbH...), domains_json TEXT (email/web domains used for matching), hq_country, city TEXT, industry TEXT, size_bucket TEXT CHECK IN ('1-10','11-50','51-200','201-1000','1001-5000','5000+','unknown'), company_type TEXT CHECK IN ('startup','scaleup','bigtech','jp_traditional','foreign_in_jp','consulting','finance','manufacturing','auto_robotics','research_lab','agency','other'), new_grad_policy_json TEXT ({accepts_2027_grads, requires_internship_first, entry_url, notes}), notes_md TEXT, created_at, updated_at
  Company facts only; the user's opinion of a company goes to user_note(target_kind='company') and profile_fact(category='company_type_pref'). new_grad_policy_json carries the 新卒 specifics from the prototype (確認在招 requires an explicit new-grad policy).
- company_alias: alias_norm TEXT PK, company_id FK, lang TEXT CHECK IN ('en','ja','zh','other'), source TEXT CHECK IN ('import','email','user','llm')
  Solves the JA/EN naming problem (e.g. 'Acme AI' vs '株式会社Acme AI' vs 'acme.example'). match_application() resolves subject 【】 tokens, LLM-extracted company names and sender domains through this table before any fuzzy matching.
- job_posting: job_id INTEGER PK, company_id FK, title, title_norm TEXT, direction_tags_json TEXT (e.g. ['applied_research','fde','mle','swe','ai_product']), industry TEXT, location_text, city, country_code CHAR(2), remote_mode TEXT CHECK IN ('onsite','hybrid','remote','unknown'), employment_type TEXT CHECK IN ('new_grad','mid_career','intern','contract','other'), hiring_status TEXT CHECK IN ('confirmed_open','to_verify','special_lead','excluded'), excluded_reason TEXT, excluded_at TEXT, excluded_source_item_id FK NULL, application_deadline TEXT NULL, salary_min, salary_max REAL, salary_currency CHAR(3), salary_period TEXT CHECK IN ('year','month','hour'), salary_basis_text TEXT, description_md TEXT, requirements_json TEXT, requires_internship_first BOOL, unconfirmed_items_json TEXT, official_apply_url TEXT, source_kind TEXT, source_id TEXT, source_url TEXT, UNIQUE(source_kind, source_id), canonical_key CHAR(40) (sha1(company_norm|title_norm|country|city_or_remote)), content_hash CHAR(64), lang TEXT, posted_at, first_seen_at, last_seen_at, verified_at TEXT, verified_source_item_id FK NULL, is_active BOOL, attribution_text TEXT NULL
  Facts of the world only (the prototype's Job + SourceEvidence). Refreshed automatically from the same source on every sighting (audit_log records content_hash changes). hiring_status='excluded' set by the user is sticky: a later sighting never flips it back, it only updates last_seen_at and a note 'still listed as of X'. Analysis (fit, gaps, growth) never lives here; see job_judgement. Never-delete rule from the prototype: exclusions keep reason, time and source.
- job_sighting: sighting_id INTEGER PK, job_id FK, watch_target_id FK NULL, seen_at TEXT, http_status INTEGER, still_listed BOOL, content_hash CHAR(64)
  One row per poll that saw (or failed to see) the posting. Three consecutive still_listed=0 -> job_posting.is_active=0 and a 'listing disappeared' application_event candidate for any linked application. This is the '核验岗位现在是否真的可以申请' mechanism; for manually entered jobs `jobpilot job verify <id>` writes a source_item(kind='manual') sighting.
- watch_target: watch_target_id INTEGER PK, kind TEXT CHECK IN ('greenhouse','lever','ashby','smartrecruiters','workable','recruitee','teamtailor','rippling','sitemap','aggregator_query','gmail_alert_filter'), company_id FK NULL, identifier TEXT (board token | site | tenant | URL), query_json TEXT (aggregator params: what/where/country/language), poll_interval_min INTEGER, last_polled_at TEXT, etag TEXT, last_modified TEXT, last_hash TEXT, enabled BOOL, attribution_required BOOL, attribution_text TEXT
  Config for the company watchlist and saved searches. detect.py fills kind/identifier from a careers URL (boards.greenhouse.io, jobs.lever.co, jobs.ashbyhq.com, ...). Per-kind token buckets (Adzuna 25/min & 250/day, JSearch 200/month, Remotive 4/day) live in settings keyed by kind.
- application: application_id INTEGER PK, company_id FK NOT NULL, job_id FK NULL (an email can prove an application exists before a posting is known), status TEXT CHECK IN ('considering','preparing','applied','assessment','interviewing','offer','accepted','rejected','withdrawn','not_fit','ghosted'), status_set_by TEXT CHECK IN ('user','auto'), status_set_at TEXT, applied_at TEXT, channel TEXT CHECK IN ('linkedin_easy_apply','company_site','ats','referral','recruiter','agency','event','manual','other'), current_stage_text TEXT, next_action TEXT, next_action_due TEXT, resume_document_id FK NULL, cover_document_id FK NULL, last_activity_at TEXT, outcome TEXT CHECK IN (NULL,'offer','accepted','rejected','withdrawn','ghosted'), outcome_at, outcome_reason TEXT, created_at, updated_at
  The user's state for one process at one company. Status is derived by ledger.derive_status(events) whenever status_set_by='auto'; once the user sets a status manually, automation may only create pending_actions ('user manual modification takes precedence over auto detection'). Ghosting is never auto-applied: applications with no activity for settings.ghost_days (30) surface as a proposal. Pipeline enum mirrors the prototype's 10 states plus accepted/ghosted.
- application_event: event_id INTEGER PK, application_id FK, event_type TEXT CHECK IN ('applied','ack','viewed','es_submitted','info_session','webtest','oa','assessment','recruiter_screen','casual_interview','interview_1','interview_2','interview_final','onsite','offer_informal','offer_formal','rejection','withdraw','listing_closed','followup_needed','scheduling','note'), stage_name TEXT, occurred_at TEXT, detected_from TEXT CHECK IN ('email','calendar','linkedin','chat','manual','rule'), source_item_id FK NULL, extraction_run_id FK NULL, rule_id TEXT NULL, confidence REAL, summary TEXT, evidence_quote TEXT, user_confirmed BOOL DEFAULT 0, created_by TEXT CHECK IN ('user','rule','llm','import'), created_at, UNIQUE(application_id, event_type, occurred_at, source_item_id)
  Append-only timeline; idempotent under re-ingest thanks to the unique key. Japanese new-grad stages are first-class (ES提出=es_submitted, 説明会=info_session, Webテスト/SPI=webtest, 内々定=offer_informal, 内定=offer_formal). derive_status maps: terminal events (accepted > offer_* > rejection/withdraw) win; else latest of interview_* -> interviewing, webtest/oa/assessment -> assessment, applied/ack/es_submitted/viewed -> applied; none -> considering.
- interview_event: interview_id INTEGER PK, application_id FK, source_item_id FK NULL (calendar event or email), calendar_event_id TEXT NULL, ical_uid TEXT NULL, round_label TEXT ('一次面接','final','recruiter screen',...), start_at_utc, end_at_utc TEXT, mode TEXT CHECK IN ('online','onsite','phone','unknown'), tool TEXT CHECK IN ('meet','zoom','teams','webex','other','unknown'), meeting_url TEXT NULL, location_text TEXT, status TEXT CHECK IN ('confirmed','tentative','cancelled','completed'), attendee_aliases_json TEXT, notes_md TEXT, updated_at
  Confirmed schedule only (prototype: confirmed interviews and pending scheduling must be separated). status='confirmed' requires a start time from the Calendar API or an explicit confirmation email; meeting_url is populated only from conferenceData.entryPoints or an explicit URL in the source, never inferred (UI shows '会議入口待確認' when NULL). Rendered in Asia/Tokyo.
- pending_schedule: pending_id INTEGER PK, application_id FK, source_item_id FK, kind TEXT CHECK IN ('pick_slot','awaiting_company','awaiting_me','self_schedule_link'), requested_at TEXT, respond_by TEXT NULL, candidate_slots_json TEXT, self_schedule_url TEXT NULL, status TEXT CHECK IN ('open','resolved','expired'), resolved_interview_id FK NULL
  Scheduling requests ('please share availability', Calendly links) live here until a confirmed time exists; resolving creates the interview_event and links it. Feeds the 'next actions' list.

- pii_alias: alias TEXT PK ('<EMAIL_12>', '<PHONE_3>', '<URL_7>', '<NAME_4>'), kind TEXT CHECK IN ('email','phone','url','name'), real_value TEXT, created_at
  Regex scrub before any LLM/embedding API call; outputs are re-hydrated locally by reverse lookup. Also the mechanism that keeps recruiter emails/phones out of default views.

  rule_stat is the classifier's own memory: when a rule's observed precision (n_confirmed/(n_confirmed+n_rejected)) drops below 0.9 its outputs stop auto-applying and become proposals; `jobpilot doctor` prints the table.

## Memory design
Five layers in one SQLite file, each with a table family and explicit update semantics.

LAYER 1 - Ledger (world facts vs. user state). World facts: company, company_alias, job_posting, job_sighting, contact, source_item. User state: application, application_event, interview_event, pending_schedule, user_note, document, job_interaction. Rule: world facts are refreshed automatically from their own source (a new sighting of the same (source_kind, source_id) overwrites job_posting fields and logs the content_hash change), but user state is never overwritten by automation once the user has touched it. Concretely: application.status_set_by='user' freezes derive_status(); job_posting.hiring_status='excluded' set by the user is sticky; user_note and job_judgement(actor='user') always outrank LLM rows.

LAYER 2 - Profile facts (typed, bi-temporal). profile_fact rows carry category/key/value, polarity (prefer|avoid|neutral|hard_require|hard_exclude), strength, confidence, source_type, evidence_quote, valid_from/valid_to, expires_at, status (candidate|active|superseded|rejected|expired), superseded_by. Lifecycle: (a) extraction yields FactCandidate with relation in {new, confirms, updates, contradicts} and related_fact_id because the extractor is always given the current active facts plus previously rejected facts ('do not re-propose'); (b) routing: 'confirms' on an existing active fact bumps confidence c' = 1-(1-c)(1-c_new) and touches observed_at (no review); 'new' auto-activates only when source_type='user_stated' (explicit first-person statement in chat, asr_confidence>=0.8 for voice), confidence>=0.85 and category not in {deal_breaker, salary_expectation, visa_status}; everything else (including all 'updates'/'contradicts', all import- and outcome-inferred facts) is status='candidate' in the memory inbox; (c) confirming an 'updates'/'contradicts' candidate runs one transaction: UPDATE old SET valid_to=now, status='superseded', superseded_by=new.fact_id; UPDATE new SET status='active', valid_from=COALESCE(valid_from, now), source_type='user_confirmed', reviewed_at=now; partial unique indexes guarantee one active value for single-valued keys (salary, remote mode, availability, notice period, visa, seniority, grad timing) and no duplicate (key, value) for multi-valued ones; (d) rejecting keeps the row (status='rejected') so the extractor and dedup logic see it; (e) TTL: availability 14 d, notice_period 90 d, salary_expectation 180 d (UI marks stale and asks to reconfirm), location/remote 365 d, personality/strengths/languages none; nightly job flips expired rows. Every change writes audit_log. profile_snapshot(hash, facts_json, rendered_md) is recomputed whenever the active set changes; the hash stamps job_judgement, search_run and rerank prompts, so staleness is a join and prompts are reproducible.

LAYER 3 - Episodic (chat_session, chat_turn, episode_summary, extraction_run). Every persisted turn (Phase 5) is a source_item(kind='chat_turn') and an extraction target; extraction_run's unique key (source_type, source_ref, prompt_version, schema_version) makes extraction idempotent and re-runnable after prompt upgrades. Summaries (summary_md, key_facts_json, open_loops_json, decisions_json) are produced every 40 turns or at session end and replace raw history in prompts; a weekly rollup with session_id NULL captures cross-session state. In Phase 3, where the host owns the transcript, chat memory enters via propose_memory_fact/propose_note tool calls whose args are stored as chat_turn rows so the fact's source_ref still resolves.

LAYER 4 - Semantic index (v1: FTS5; v1.5: + sqlite-vec). v1 retrieval = fts_ledger (unicode61) and fts_memory plus a trigram table for CJK and a LIKE fallback for 1-2 character CJK tokens, fused with RRF; v1.5 adds chunk rows for jobs/emails/notes/facts/summaries embedded locally with bge-m3 (1024-d) into vec_chunks_bgem3 (PARTITION KEY kind) and hybrid RRF(vec top-50, fts_latin top-50, fts_cjk top-50). embedding_index records model/dims so a model swap is a new table and an explicit re-embed, never a silent mix.

LAYER 5 - Behavioural signals (job_interaction, fit_signal, preference_weight, job_feature, search_run). This is where the loop closes: profile facts -> w_stated (recomputed from polarity*strength per feature on each snapshot change) -> soft score over job_feature -> LLM rerank with the rendered profile block, an outcome summary from fit_signal ('3 rejections at 5000+ companies, 2 interviews at startups') and verbatim dismissal reasons -> search_run/search_run_result -> shown -> job_interaction (shown/ignored/saved/compared/dismissed/applied) and application outcomes (rejection/offer events -> fit_signal) -> (v2) nightly SGD update of w_learned with labels +1 applied, +0.5 saved, -1 dismissed, -0.25 ignored (>=3 shows), 90-day half-life, blended 0.7 stated + 0.3 learned -> next search. Company-side rejections deliberately update fit_signal only (realism context), not preference weights (the user's taste). Pattern detectors over Layer 5 emit outcome_inferred FactCandidates ('you dismissed 5 consulting roles - add company_type_pref avoid consulting?') into the same inbox, so the profile grows from behaviour but only with consent.

Prompt rendering: system = [static instructions (cache breakpoint)] + [rendered profile block from the current snapshot (cache breakpoint)] + volatile parts (today's date, retrieved chunks, recent summaries) after the breakpoint. The model never receives the whole DB; retrieval tools are bounded (limit<=20) and return stable ids the model must cite.

Precedence matrix (the core of 'memory-update semantics', tested in tests/test_precedence_matrix.py): actor user > rule (precision>=0.95 templates) > llm > import for user-state rows; world-fact rows follow their source; any automated write that would change a row last touched by actor='user' becomes a pending_action instead; ambiguous application matches always become pending_actions with candidates_json; interview times parsed from prose (not Calendar API) are tentative until confirmed; ghosting is proposed, never applied. Undo = replay audit_log.before_json.

## Read-only guarantee
Six independent layers, each testable, so a policy lapse in one cannot produce an external write.

1) Credential layer: the only Google scopes ever requested are https://www.googleapis.com/auth/gmail.readonly and https://www.googleapis.com/auth/calendar.events.readonly; SCOPES is a frozenset constant in sources/google_auth.py, and connection start asserts set(token.scopes) <= SCOPES, deleting the token and aborting otherwise. These scopes cannot send, draft, label, modify, trash, delete or insert (the API responds 403 insufficient scopes). No IMAP/SMTP path exists (XOAUTH2 IMAP would need the full mail.google.com scope). LinkedIn has no credentials at all: the connector is a ZIP/CSV parser with zero network imports; OIDC sign-in is not implemented. Aggregator keys (Adzuna, JSearch) are search-only APIs.

2) Transport layer: every non-Google HTTP call goes through sources/base.py GetOnlyClient(httpx.Client), whose request() raises ReadOnlyViolation for any method other than GET/HEAD unless (host, path-prefix) is in an explicit STATELESS_SEARCH_POST allowlist (empty in v1; Workday cxs/Jooble search may be added in v2 with a comment citing that they create no server-side state). Google calls go through ReadOnlyGmail/ReadOnlyCalendar facades that expose only profile(), list_messages(), get_message(), list_history(), list_events(); the underlying googleapiclient resource is a private attribute and is never returned.

3) Static layer: ruff [tool.ruff.lint.flake8-tidy-imports.banned-api] bans smtplib, imaplib, poplib and 'googleapiclient' outside sources/; tests/test_readonly_guarantee.py walks src/jobpilot/sources and fails on any of the tokens .send( .modify( .trash( .untrash( .delete( .insert( .import_( .batchModify( .batchDelete( .create( .update( .patch( .watch( .stop( drafts( labels( settings( ; it also asserts jobpilot.core imports nothing from httpx, googleapiclient or requests, and that no module contains 'linkedin.com/voyager', 'li_at' or 'playwright'.

4) Protocol layer: Source is a Protocol with backfill(), pull_incremental(cursor), describe() only; ingest.py is the sole consumer and writes only to source_item. Type-checked by pyright; a test instantiates every registered source and asserts its public surface equals the Protocol's.

5) Tool layer: every MCP/agent tool is registered through jobpilot.tools.registry with a mandatory side_effect Literal['none','local_db']; the registry rejects anything else at import time; a test asserts the MCP server module and the pydantic-ai toolset import nothing from jobpilot.sources, so no chat turn can even reach a connector. Read tools carry readOnlyHint annotations (hints only; not relied upon).

6) Human layer for local state: anything an LLM, rule or import wants to change that touches user-set rows goes through pending_action -> confirm_action, and in Phase 3 the host's per-tool approval prompt is a second gate; in Phase 5 confirmation is matched deterministically outside the model. The system prompt forbids claiming that anything was sent, applied or changed unless a confirm_action result says so, and the UI never renders a 'send'/'reply'/'apply' control - there is no code path behind such a button to begin with.

Operational corollaries: the Gmail API never marks messages read on get; no labels are created; the LinkedIn archive is requested by the user in a browser, not by Mita JobPilot; job-board polling honours robots.txt via protego, uses a descriptive User-Agent, and never posts to ATS application endpoints. Adding any write capability later would require changing SCOPES, the GetOnlyClient allowlist, the banned-api list and the registry Literal simultaneously - four deliberate, reviewable edits.

## Top risks
- Gmail refresh token dies every 7 days while the consent screen is in Testing (personal accounts cannot use Internal), silently stopping ingestion. -> Publish the consent screen to 'In production' without verification (allowed for personal use), delete token and re-consent so the new refresh token is off the 7-day clock; startup token-health check on invalid_grant relaunches the loopback flow; `jobpilot doctor` shows token age and scopes; sync_state.last_error surfaces in every view.
- Over-automation pollutes the ledger: a mis-classified お祈りメール or a recruiter newsletter flips an application to 'rejected' or creates phantom applications, destroying trust in the tracker. -> Precedence matrix + pending_action choke point (user-set rows are never auto-overwritten; new applications and ambiguous matches are always proposals); rule_stat tracks per-rule precision and demotes rules below 0.9 to proposal-only; audit_log before/after enables one-command undo; 'auto' badges on every unconfirmed row; synthetic EN/JA/ZH fixtures in tests_rules_classifier.
- Linking emails/calendar events to the right application is hard in a JA/EN/ZH inbox (company names in 【】, agencies mailing on behalf of companies, several processes at one company). -> company_alias table (NFKC + suffix stripping, populated from imports and confirmed matches), sender-domain -> company.domains_json, Gmail threadId stickiness (a thread linked once stays linked), rapidfuzz on role titles, and candidates_json on pending_actions so the user picks from 2-3 options instead of typing; agencies modelled as company_type='agency' contacts, not as the employer.
- Schema churn as real data reveals gaps, tempting ad-hoc edits that break provenance. -> Migrations from day 0; JSON columns for the genuinely fuzzy parts (payload_json, class_json, features_json, requirements_json); raw source_items retained so any derived table can be rebuilt with `jobpilot rederive --prompt-version`; ADRs record why each table exists.
- LinkedIn data is stale or incomplete (only Easy Apply and confirmed external applications appear; messages need the 24 h archive) and the temptation to automate the logged-in site grows. -> Design explicitly forbids automation (guarantee test greps for voyager/li_at/playwright); Gmail LinkedIn notifications give near-real-time signals; in-app checklist and '>14 days old' nudge for re-requesting the archive; 'Did you apply?' discipline; manual/voice log-application tool covers the rest.
- LLM cost and latency during backfill (thousands of emails) or noisy job feeds. -> Rules gate first (most ATS/alert/calendar mail never reaches the LLM); metadata-only fetch for non-gated mail; extraction_run cache keyed by prompt/schema version; effort='low' for bulk classification; per-route model choice in settings (opus-5 default, cheaper tiers selectable by the user); monthly cost query in `jobpilot doctor`; hard filters in SQL before any rerank call.
- Japanese/Chinese text handling degrades matching and search (full-width characters, company suffixes, FTS tokenization). -> NFKC normalization everywhere before hashing/matching; suffix table incl. 株式会社/(株)/合同会社; dual FTS tables (unicode61 + trigram) with LIKE fallback for short CJK; lang column on postings/facts/chunks; bge-m3 chosen for CJK+EN when vectors arrive.
- Privacy leakage: recruiter PII, email bodies or resume contents sent to LLM/embedding APIs or shown on screen. -> pii_alias scrubbing before every external call with local re-hydration; body trimming and quoted-reply stripping; local embeddings by default; contacts rendered as aliases unless opened explicitly; body_text purge after 90 days; DB under %LOCALAPPDATA% and gitignored; SQLCipher in Phase 6; Windows Device Encryption checked via msinfo32.
- Solo-developer scope creep (UI polish, wake words, more connectors) stalls the phases that deliver daily value. -> Phase 1 is deterministic and useful in a week; chat and voice arrive in Phase 3 with zero UI code via MCP hosts; the web UI is Phase 5 with a NiceGUI fallback; each phase has exit criteria that are queries against the DB, not features.
- External tool drift: MCP SDK 2.x rework, host behaviour changes (Claude Desktop voice + tools), pydantic-ai API changes, OpenAI model ID churn. -> Views are thin adapters over core services; model IDs and provider come from settings; pinned versions in uv.lock; a smoke test runs the MCP server with the inspector; the CLI remains a complete fallback view for every capability.
