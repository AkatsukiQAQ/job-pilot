# Proposal P0 (mvp): MVP-first. The thinnest slice that changes the job hunt this week is: Gmail (read-only OAuth) -> rule+LLM-classified application events -> one SQLite file -> a `jobpilot board` CLI table plus a 4-tool local MCP server, so Claude Desktop / Claude Code (Claude) and Codex CLI (GPT) are the chat and voice UI from day 5 with zero UI code. LinkedIn = notification emails now, official ZIP export import in week 2. Google Calendar, memory, job search, own web UI, push-to-talk are later phases that all plug into the same DB and the same static tool registry. Phase 1 deliberately excludes everything that is not "what is the state of every selection process I am in, kept current automatically".
Mita JobPilot v1 is a read-only, Gmail-fed SQLite tracker of every job selection process (potential/in-progress/finished) with a CLI board and a local MCP server, so the user's existing Claude/GPT desktop clients become the chat+voice interface immediately; later phases add LinkedIn archive import, Calendar interviews, a typed profile memory, a memory-driven job search that learns from outcomes, and finally an own web UI with push-to-talk — all writing only to the local DB, never to any external service.

## Data flow
Gmail API (GET only, via ReadOnlyHttp) -> email_message rows (metadata for all, full body only for gated mail) -> rules gate (rule_id) -> LLM classify for gated/ambiguous (cached by gmail_id+prompt_version) -> email_classification -> pipeline resolver upserts company + application + application_event and recomputes application.auto_status/next_action_due -> read by `jobpilot board` and by MCP read tools inside Claude Desktop / Claude Code / Codex (voice via Claude Desktop voice mode or Win+H dictation) -> user corrections and notes flow back only through propose_* -> pending_actions -> confirm_action -> user_status / notes / profile_facts (+ audit_log). Phase 2 adds LinkedIn ZIP -> li_* tables -> application (channel linkedin_easy_apply). Phase 3 adds Calendar -> interview_event -> application. Phase 4 adds boards/alerts -> job_posting -> dedupe -> hard filters (profile_facts) + soft score (preference_weights) + LLM rerank -> job_scores -> shown -> job_interactions (saved/dismissed/applied) and application outcomes -> (Phase 6) learn.py updates preference_weights.w_learned and fit_signals -> next search ranks differently. Every arrow into an external service is a GET; every write lands in jobpilot.db.

## Phases
### Phase 1 - Inbox to Board (MVP) (5-7 evening sessions (~18-22 hours) in the first week)
Goal: Within one week, every job selection process from the last 180 days that left a trace in Gmail appears on a status board with correct stage, next deadline and last event, and new mail updates it within ~2 minutes, with zero external writes possible. ## Memory design
Four layers in the one SQLite file, added incrementally, with the learning loop living in three places (search/scoring.py reads it, search/learn.py updates it, the job_interactions + application_event ledgers feed it). Layer 1 (Phase 1) - structured history: company, application (auto_status vs user_status, effective_status generated), application_event append-only ledger (idempotent UNIQUE key), interview_event (Phase 3), li_* import tables (Phase 2). This is 'positions applied to and their outcomes' and is fully populated by Gmail/Calendar/LinkedIn ingestion without any LLM opinion in the primary keys. Layer 2 (Phase 3) - typed profile: profile_facts rows with category (role_target, salary_expectation, location_pref, remote_pref, company_type_pref, company_size_pref, industry_pref, tech_pref, culture_pref, work_style, deal_breaker, personality, strength, weakness, language, visa_status, availability, graduation...), dotted key, value, polarity (prefer|avoid|neutral|hard_require|hard_exclude), strength, confidence, source_type, evidence_quote, bi-temporal valid_from/valid_to plus status (candidate|active|superseded|rejected|expired) and superseded_by - Graphiti's edge-validity idea in a table. Sources: user statements in chat (proposed by the model via propose_memory_fact in Phases 3-4, extracted automatically after each turn in Phase 5), LinkedIn Job Seeker Preferences, outcome inference (Phase 6). Nothing becomes active without the user (auto-accept only for explicit first-person statements, confidence >= 0.85, non-sensitive categories). Active facts are rendered by memory/render.py into a stable Markdown block (Letta-style pinned core memory) exposed as get_profile() and the jobpilot://profile MCP resource and placed behind a prompt-cache breakpoint. Layer 3 (Phase 5) - episodic: chat_sessions/chat_turns (modality, asr_confidence) and episode_summaries (summary_md, key_facts_json, open_loops_json) consolidated every 40 turns; extraction_runs make extraction idempotent (UNIQUE(source_type, source_ref, prompt_version, schema_version)) and audit cost. Layer 4 (Phase 3 FTS, Phase 6 vectors) - retrieval: memory_fts + email_fts twins (unicode61 for Latin, trigram for CJK with LIKE fallback for 1-2 char queries), later chunks + vec0 (bge-m3 1024-d cosine) fused by RRF. The loop: profile_facts (hard_* polarity) become SQL WHERE clauses in scoring.py; prefer/avoid facts set preference_weights.w_stated; job_features are computed per canonical job; job_scores stores the transparent soft score plus the LLM rerank with profile_snapshot_hash so a changed profile re-scores; every shown job is logged, every save/dismiss/apply is logged in job_interactions, every company-side outcome lands in application_event and fit_signals; learn.py (Phase 6, nightly) turns interactions into w_learned (applied +1, saved +0.5, dismissed -1, ignored x3 -0.25; 0.7/0.3 blend; 90-day half-life) and proposes outcome_inferred candidate facts (e.g. 'you never apply to 5000+ companies') into the memory inbox for confirmation - so the system gets smarter from outcomes but the user stays the final editor of their own profile. Expiry: availability 14d, notice_period 90d, salary_expectation 180d (stale flag, reconfirm prompt), personality never. Privacy: PII aliases (pii_aliases) replace emails/phones/URLs before any API call; body_text purged after 90 days once events are derived; Phase 6 SQLCipher with a DPAPI-held key.

## Read-only guarantee
Five independent layers, each sufficient on its own, all testable. (1) Credential scope: the Google OAuth token is minted with exactly {gmail.readonly} (+ calendar.events.readonly from Phase 3); Google's servers reject every write method (messages.send/insert/modify/trash/delete, drafts.*, labels.*, events.insert/patch/delete) with 403 insufficient scopes regardless of what the code does. `jobpilot auth google` asserts set(creds.scopes) <= ALLOWED_SCOPES before persisting token.json and the watch loop re-checks on startup. (2) Transport: every Google request goes through ReadOnlyHttp, a google_auth_httplib2.AuthorizedHttp subclass whose request(uri, method='GET', ...) raises WriteAttempted for any method other than GET (the /batch endpoint is not used); job-board HTTP in Phase 4 uses an httpx GetOnlyTransport with the same rule; there is no SMTP, IMAP, or browser-automation client in the dependency tree at all. (3) Code surface: jobpilot.connectors exposes only fetch_*/list_*/get_*/import_* functions; LinkedIn has no network code whatsoever (ZIP from disk); tests/test_readonly_guard.py imports every module under src/jobpilot and fails if any public symbol name in connectors matches ^(send|post|apply|label|modify|trash|delete|insert|create_draft|reply|message|watch_push), if any module imports smtplib, imaplib, playwright, selenium, linkedin_api, or if any source file contains 'linkedin.com/voyager'; a test also asserts the pinned Google scopes list is unchanged. (4) Tool registry: the LLM/MCP tool list is a static allowlist in jobpilot.tools.registry built from readonly.py and local_mutations.py; every tool declares side_effect in {'none','local_db'}; tools may not import jobpilot.connectors (import-graph test); local mutations are two-phase (propose_* -> pending_actions -> confirm_action) so the model never executes a state change directly, and hosts (Claude Desktop, Claude Code, Codex) add their own per-tool approval prompt; in Phase 5 confirmation comes from a UI click or a deterministic regex on the transcript, executed by application code. (5) Data direction: the only outbound payloads that are not GETs are LLM/embedding API calls carrying aliased, truncated text; no external system ever receives an instruction from Mita JobPilot. Job-search sources with POST-based search (Workday cxs, Jooble) are excluded until Phase 6 and then only via an explicit per-endpoint allowlist that the transport checks.

## Top risks
- Google OAuth refresh token expires every 7 days while the consent screen is in Testing, silently stopping sync. -> At the end of Phase 1 click 'Publish app' (In production) without submitting for verification (personal use is exempt), delete token.json and re-consent; add a startup token-health check that catches invalid_grant and relaunches run_local_server; log the last successful sync time on the board so staleness is visible.
- Classifier mislabels Japanese pass/fail mails that share subjects (選考結果のご連絡) or misses in-app-only notifications from company マイページ systems, so the board is wrong or incomplete. -> Rules never decide pass vs fail; LLM outputs confidence and anything < 0.7 lands in a needs-review queue instead of changing auto_status; user_status always overrides; `jobpilot log`/propose_log_application covers channels that never email; `jobpilot senders` surfaces new sender templates weekly for rules refinement; spot-check exit criterion in Phase 1.
- Temptation to automate LinkedIn (Playwright, li_at cookies, Unipile) leads to account restriction in the middle of a job hunt. -> No LinkedIn network code exists in the repo by design; test_readonly_guard fails on playwright/linkedin_api imports or 'voyager' strings; the official ZIP export plus Gmail notifications are documented as the only channels, with a README risk note citing User Agreement 8.2 and the 2022-2026 enforcement record.
- UI scope creep pulls effort away from data correctness (the product baseline describes a rich workbench). -> Phases 1-4 ship no UI beyond the CLI and MCP tools; Claude Desktop/Claude Code/Codex are the chat and voice surfaces; Phase 5 is gated on Phase 3 exit criteria being met and starts with a single page; NiceGUI mounted on the same FastAPI app is the documented fallback if the Vite toolchain stalls.
- Application resolution merges or splits processes incorrectly (same company, two roles; recruiter mail with no role). -> UNIQUE(company_id, role_norm) plus Gmail thread_id tie-breaker; events with unknown role attach to the company's single open application or create a 'role unknown' application flagged for review; `jobpilot merge <a> <b>` and `jobpilot split` CLI commands in Phase 2 write audit_log; events are append-only so re-resolution is possible.
- history.list startHistoryId becomes invalid (404) or Gmail rate limits during backfill. -> On 404 resync from newest stored internalDate using messages.list q='after:YYYY/MM/DD'; sequential messages.get with exponential backoff (max 64 s) on 429/403 rateLimitExceeded; backfill of ~5k messages costs ~100k units, well under the 6k units/min/user ceiling within ~20 minutes.
- LLM cost or privacy drift as more text is sent (emails, chat, postings). -> Cache by (gmail_id, prompt_version); rules gate keeps job_alert digests and non-job mail away from the LLM; PII aliasing and 4k-char truncation before every call; extraction_runs logs tokens and cost_usd; classifier defaults to Sonnet 5 with a Haiku 4.5 switch; nothing but aliased text, postings and the profile block leaves the machine.
- Windows-specific setup failures (Claude Desktop cannot find uv, relative paths, uv 0.10 scaffold lacks a build backend, Credential Manager blob limits). -> Use the absolute uv path from `where uv` in claude_desktop_config.json and claude mcp add; run `uv self update` then add [build-system] uv_build and console scripts before anything else; keep only short API keys in keyring and store the Google token as a DPAPI file in Phase 2; check %APPDATA%\Claude\logs\mcp-server-jobpilot.log on failure.
- Model IDs and SDK APIs drift (mcp 2.x already renamed FastMCP to MCPServer; model ids change). -> All model ids live in settings.py/.env, never in code; pin mcp==2.2.*, pydantic-ai-slim==2.43.*, google-api-python-client==2.200.* in pyproject; a smoke test calls each configured model once on `jobpilot doctor`.
