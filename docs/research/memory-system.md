# 记忆系统设计

> **AI 调研附录**（生成于 2026-09-16，英文）。内容由并行调研 agent 对照官方页面整理，verified/unverified 标注以原文为准；实现前需再次核对。相关更正见 japan-critique.md 与 proposal-judgments.md。

# Memory system for a personal job-search agent (Mita JobPilot): layers, extraction pipeline, memory-driven job scoring, local-first privacy, embeddings, concrete schema, phased build order

## Summary
All four memory layers can live in ONE local SQLite file on this machine, verified empirically today: the uv-managed CPython 3.12.12 ships SQLite 3.50.4 with `Connection.enable_load_extension` available and FTS5 compiled in; `sqlite-vec` v0.1.9 (latest stable, 2026-03-31) loads and answers KNN queries with `distance_metric=cosine`, PARTITION KEY filtering and `+aux` columns; the FTS5 `trigram` tokenizer indexes Japanese/Chinese substrings (with the known gap that 1-2 character CJK queries need a `LIKE` fallback); and the official `sqlcipher3` 2.6.0 wheel (SQLCipher 4.12.0 community, SQLite 3.51.1, ENABLE_LOAD_EXTENSION + FTS5) installs on Windows and sqlite-vec loads on an encrypted connection, so encryption-at-rest, vectors and full-text can coexist in one file. No vector-DB server or graph database is needed. Off-the-shelf memory frameworks are poor fits as dependencies for a single-user typed memory: mem0 OSS v2.0.x (2026) switched to a single-pass ADD-only algorithm (no write-time UPDATE/DELETE, conflicting facts accumulate and are resolved only by retrieval ranking) and removed graph stores from the OSS SDK; Letta requires Postgres+pgvector and its Docker image is "no longer an actively maintained or supported Letta product surface"; Graphiti requires Neo4j 5.26+/FalkorDB 1.1.2+ (Kuzu deprecated); LangMem is still 0.0.30 (Oct 2025). Borrow their designs instead: Graphiti's bi-temporal edge fields (created_at/valid_at/invalid_at/expired_at) for profile-fact supersession, Letta's pinned "core memory blocks" (render active profile facts into a cached system-prompt block), and mem0's fused semantic+BM25 retrieval. Extraction should use provider-native schema-constrained outputs (Claude `client.messages.parse(output_format=PydanticModel)` / `output_config.format`; OpenAI `client.responses.parse(text_format=Model)` with strict JSON schema) that emit candidate facts with evidence quotes, confidence, and an explicit relation to existing fact_ids (new/confirms/updates/contradicts), landing in a review inbox (`status='candidate'`) before becoming active. Job search consumes memory as SQL hard filters (hard_exclude/hard_require facts) + a weighted soft score (stated weights blended with weights learned online from applied/saved/dismissed/ignored actions) + an LLM rerank of the top-K with structured per-job explanations, while a `job_interactions` ledger plus `canonical_key`/`content_hash` dedupe guarantees seen/applied jobs are never re-shown. For CJK+EN embeddings run locally by default: bge-m3 dense (1024-d, 8k ctx; strongest evidence for Japanese) is the safe v1 choice, Qwen3-Embedding-0.6B is best for zh/en but reported weak on JMTEB, and voyage-4-nano (Apache-2.0, ~340M params, shares vector space with the voyage-4 API models) lets you start local and upgrade to API embeddings without re-indexing; API embeddings (voyage-4 $0.06/M with 200M free tokens, OpenAI text-embedding-3-large $0.13/M, Gemini $0.15-0.20/M) send text off-machine, so restrict them to public job-posting text. Anthropic offers no embeddings API. Nothing in this design requires write access to Gmail, LinkedIn or any external service.

## Hard constraints
  - Read-only externally: the memory system stores Gmail message/thread IDs, LinkedIn URLs and hashes as provenance keys only; it never labels, archives, sends, or writes back. All writes are to the local SQLite file.
  - Runtime verified on this machine (2026-09-16): uv-managed CPython 3.12.12 (%USERPROFILE%\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none), SQLite 3.50.4, `enable_load_extension` present, compile options include ENABLE_FTS5, ENABLE_FTS3/4, ENABLE_RTREE, JSON functions available. Do not assume this for other interpreters (python.org/conda builds may lack extension loading).
  - sqlite-vec stable is v0.1.9 (2026-03-31): brute-force KNN only; ANN (DiskANN/IVF/rescore) exists only in v0.1.10 alphas (latest alpha.4, 2026-05-18). vec0 columns have fixed dimensionality; a model change means a new vec0 table and full re-embed.
  - FTS5 `trigram` tokenizer (SQLite >= 3.34) requires >= 3 characters per query token; 1-2 character CJK queries return nothing (verified) and must fall back to `LIKE '%..%'` on `chunks.text`. Keep a separate unicode61 table for Latin text so BM25 ranking stays clean.
  - If encryption-at-rest via SQLCipher is adopted: use the `sqlcipher3` module (official wheels >= 0.6.2; tested 2.6.0 = SQLCipher 4.12.0 community, SQLite 3.51.1) for every connection instead of stdlib `sqlite3`; `PRAGMA key` must be the first statement; SQLCipher 4 format; sqlite-vec and FTS5 load on it (verified). Other processes/tools (DB Browser, PyCharm DB tool) must also support SQLCipher 4 to open the file.
  - Windows 11 Home has Device Encryption (not full BitLocker management); since 24H2 the HSTI/Modern Standby/DMA prerequisites are removed, but on a device using only local accounts it 'remains unprotected even though the data is encrypted' (clear key) until a Microsoft account backs up the recovery key. Check msinfo32 'Device Encryption Support' and Settings > Privacy & security > Device encryption before relying on it.
  - Anthropic has no embeddings API; embeddings must come from a local model or a third-party API (Voyage recommended by Anthropic docs, or OpenAI/Gemini).
  - Provider structured outputs: Claude via `client.messages.parse(model=..., output_format=PydanticModel)` (or `output_config={'format': {'type':'json_schema','schema':...}}` on `messages.create`; `output_format` on `create` is deprecated); OpenAI via `client.responses.parse(model=..., input=..., text_format=PydanticModel)` (`text.format` json_schema strict). Both require closed schemas (`additionalProperties: false`, all properties required). Do not rely on assistant prefill (rejected by current Claude models).
  - Default Claude model for extraction/rerank per current guidance: `claude-opus-5` (adaptive thinking; use `output_config.effort='low'|'medium'` for bulk extraction); `claude-sonnet-5` / `claude-haiku-4-5` only if the user explicitly opts for cheaper tiers. Check `stop_reason` before parsing.
  - Every embedding row must record `model_name` and `dims`; query embeddings must use the same model and, for asymmetric models, the correct prefix/instruction (`query: `/`passage: ` for multilingual-e5; `input_type='query'|'document'` for Voyage; instruction prompt for Qwen3-Embedding; ruri-v3 `検索クエリ: `/`検索文書: `).
  - Voice commands and chat turns are memory sources but the profile must never be silently overwritten by low-confidence extraction: only `status='candidate'` -> user confirm (or explicit first-person statements above a confidence threshold) may become `active`.
  - Secrets (Anthropic/OpenAI/Voyage keys, Gmail OAuth refresh token, SQLCipher key) live in Windows Credential Manager (`keyring`) or DPAPI blobs (`win32crypt.CryptProtectData`), never in the SQLite DB or repo. Credential Manager entries have a small payload limit (documented 2560 UTF-16 chars; failures observed around 700 chars on some machines) - use DPAPI-encrypted files for anything larger.

## Recommendation
V1 (first 2-3 weeks): Option A only. Create one SQLite database (WAL, foreign_keys=ON) at %LOCALAPPDATA%\JobPilot\jobpilot.db (or <repo>\data\, git-ignored) with the schema below. Implement Layer 1 (companies/jobs/applications/application_events/contacts/documents/source_items) and Layer 2 (`profile_facts` with polarity/strength/confidence/source/valid_from/valid_to/superseded_by/status) first, then Layer 3 chat persistence (`chat_sessions`, `chat_turns`). Wire extraction immediately: after every user chat turn and every job-related email, one structured-output call (`MemoryExtraction` Pydantic schema via `client.messages.parse`, or `responses.parse` when GPT is selected) with the current active facts + previously rejected facts in context so the model returns `relation` = new/confirms/updates/contradicts with `related_fact_id`. Candidates go to a "memory inbox" (status=candidate); user confirms/edits/vetoes; `updates`/`contradicts` on confirm sets old.valid_to=now, old.status='superseded', old.superseded_by=new.fact_id. Render active facts into a stable, cached system-prompt block (Letta-style core memory) for the chat. For retrieval in v1 use FTS5 only (dual tables: unicode61 + trigram, RRF-fused, LIKE fallback for short CJK) - no embeddings yet. For job search in v1: dedupe by `canonical_key` + `content_hash`, log every `shown/ignored/saved/dismissed/applied` in `job_interactions`, exclude anything with an interaction or application, apply hard filters from `hard_exclude`/`hard_require` facts in SQL, compute a transparent weighted soft score from stated facts (`preference_weights.source='stated'`), and LLM-rerank the top 20-30 with a `RerankResult` structured output stored in `job_scores` with `profile_snapshot_hash`, model and prompt_version. Store secrets in `keyring`; skip SQLCipher initially but abstract the connection factory so swapping `sqlite3` -> `sqlcipher3` is one function.

V1.5 (weeks 3-4): add `sqlite-vec` + local embeddings (bge-m3 dense via sentence-transformers or Ollama `bge-m3`; fallback multilingual-e5-base via fastembed ONNX if CPU is too slow) over a `chunks` table; hybrid retrieval = RRF(vec KNN top-50, fts_latin top-50, fts_cjk top-50); optional local cross-encoder rerank (BAAI/bge-reranker-v2-m3). Add episodic summarization: on session close write `episode_summaries` (summary_md, key_facts_json, open_loops_json) and feed the last N summaries + active facts into the system prompt instead of raw history.

V2 (month 2): outcome learning - online logistic/SGD update of `preference_weights.source='learned'` from applied(+1)/saved(+0.5)/dismissed(-1)/ignored-3x(-0.25); company-side rejections go to `fit_signals`, not preference weights; blend w = 0.7*stated + 0.3*learned, half-life decay 90 days for learned. Expiry job: `expires_at` per category (availability 14d, salary expectation 180d -> mark stale and ask to reconfirm; personality none), purge raw `source_items.body_text` after a configurable window while keeping derived events. Migrate to SQLCipher (`sqlcipher3`, raw 32-byte key stored via DPAPI; `ATTACH ... KEY` + `sqlcipher_export()` to convert). Add the PII alias layer (`pii_aliases`) so emails/phones/URLs are pseudonymized before leaving the machine. Optionally switch job-posting embeddings (public text) to voyage-4 API, or start with voyage-4-nano locally to keep that door open without re-indexing.

Defer/skip: mem0, Letta, Graphiti, LangMem, Cognee as dependencies (take their designs, not their runtimes); ANN indexes until sqlite-vec 0.1.10 is stable or vectors exceed ~200k; a graph store - if cross-entity reasoning is needed later, add an `entity_edges(source_id, target_id, relation, fact, valid_at, invalid_at, created_at, expired_at, episode_ref)` table in SQLite mirroring Graphiti's EntityEdge.

## Options
### A. SQLite-only memory stack: stdlib sqlite3 + sqlite-vec + FTS5 (unicode61 + trigram) + custom typed memory model, optional SQLCipher [read_only_ok=True, cost=$0 infrastructure; LLM cost only for extraction/rerank (one Sonnet/Haiku-class call per chat turn or job-related email; roughly $1-10/month at personal volume), effort=days, risk=none]
One file (WAL mode) holds all four layers: structured job/application tables, typed `profile_facts` with bi-temporal supersession, chat turns + episodic summaries, and a `chunks` table indexed by a vec0 virtual table and two FTS5 external-content tables. Extraction and reranking via Claude/OpenAI structured outputs. Verified working on this machine (Python 3.12.12, SQLite 3.50.4, sqlite-vec 0.1.9, sqlcipher3 2.6.0).
Pros:
  - Zero servers; one backup-able file; transactional consistency between facts, vectors and FTS
  - Brute-force KNN is fine at this scale (~20k-100k vectors x 1024 float32 = 80-400 MB); ANN (DiskANN/IVF) is arriving in sqlite-vec 0.1.10 alphas
  - FTS5 trigram gives CJK substring search out of the box; unicode61 gives BM25 for EN
  - SQLCipher path verified: sqlite-vec + FTS5 load on an encrypted `sqlcipher3` connection
  - Full control over typing, provenance, review/veto, expiry - things frameworks do not expose
Cons:
  - You write the extraction, dedup and supersession logic yourself (a few hundred lines)
  - sqlite-vec vec0 tables have fixed dims per table: changing embedding model = new table + full re-embed
  - Trigram cannot match 1-2 char CJK queries; needs LIKE fallback (verified)
  - If SQLCipher is adopted, every connection must use `sqlcipher3` instead of `sqlite3`
### B. SQLite facts + LanceDB (embedded) for the semantic index [read_only_ok=True, cost=$0, effort=days, risk=none]
Keep layers 1-3 in SQLite; put chunks/embeddings in LanceDB (Rust, Arrow-native, `lancedb` 0.38.0 released 2026-08-31, Windows x86-64 wheels, Python >=3.10) using its built-in hybrid search (`query_type='hybrid'` + RRFReranker) and IVF/HNSW indexes.
Pros:
  - Hybrid BM25+vector with rerankers built in; ANN indexes available now
  - Table versioning (time travel) and multimodal columns if you later store resume PDFs/screenshots
Cons:
  - Second storage engine and on-disk format; cannot live inside the SQLCipher file
  - pyarrow dependency and larger install; its FTS tokenizer's CJK behaviour must be verified (SQLite trigram is known-good)
  - Cross-store consistency (delete a job -> delete its vectors) becomes your job
### C. SQLite facts + Chroma PersistentClient (chromadb 1.5.9, Rust core) [read_only_ok=True, cost=$0, effort=days, risk=none]
Embedded Chroma via `chromadb.PersistentClient(path=...)`; metadata filters incl. `$regex`, `$contains` (1.5.x). Latest PyPI 1.5.9 (2026-05-05).
Pros:
  - Simplest vector API; active weekly release cadence; Apache-2.0
  - Handles embedding function plumbing for you
Cons:
  - ~22 MB wheel; separate store outside SQLCipher
  - Chroma's own full-text (trigram) has had CJK edge cases (issue #1073); you would still want SQLite FTS5 for keyword search
  - Less control over hybrid fusion than A or B
### D. Qdrant local mode (`QdrantClient(path=...)`) or Qdrant Edge [read_only_ok=True, cost=$0, effort=days, risk=none]
Pure-Python local mode persists to SQLite-backed files; Qdrant Edge is an in-process shard library with a different `EdgeShard` API.
Pros:
  - Same API as Qdrant server if you ever scale out
  - fastembed integration
Cons:
  - Local mode is brute force, warns above ~20k points, single-process file lock, data format incompatible with server; documented as for tests/notebooks only
  - Edge is a different API surface and adds little over sqlite-vec for one user
### E. mem0 OSS (Python SDK v2.0.x, latest v2.0.20) as the memory layer [read_only_ok=True, cost=$0 + LLM calls, effort=hours, risk=none]
Apache-2.0 `add()/search()` memory layer. v2.0.0 (2026-04-16) introduced a one-LLM-call ADD-only pipeline ('No separate UPDATE/DELETE pass'), fused semantic + BM25 + entity-boost scoring, removed Neo4j/Memgraph/Kuzu/AGE drivers (~4,000 lines) in favour of built-in entity linking; defaults: Qdrant vectors + SQLite history + OpenAI.
Pros:
  - Turnkey extraction and hybrid retrieval; supports Chroma/FAISS/Qdrant-local backends and Anthropic/OpenAI LLMs
  - Good reference for prompt design (inclusion/exclusion prompts, metadata filters)
Cons:
  - Memories are untyped strings; no schema for salary/location/deal-breakers, no polarity/strength, no user review step
  - v2 ADD-only design means contradictory preferences accumulate; you cannot express 'this supersedes that' at write time
  - Graph memory is Platform-only now; another abstraction layer over storage you already own
### F. Letta (formerly MemGPT) self-hosted server [read_only_ok=True, cost=$0 self-hosted (Pro cloud $20/mo not needed), effort=weeks, risk=none]
Apache-2.0 agent runtime with agent-editable core memory blocks pinned in the system prompt, archival memory, shared blocks; supports Anthropic/OpenAI/Ollama via env vars.
Pros:
  - Proven self-editing memory blocks pattern; persistence of all agent state
  - Model-agnostic
Cons:
  - Requires Docker + PostgreSQL with pgvector (`LETTA_PG_URI`); docs state the Docker image 'is no longer an actively maintained or supported Letta product surface'
  - Company focus moved to Letta Code / desktop app in 2026; framework lock-in; heavyweight for a one-user local tool
  - Memory is free-text blocks, not typed facts you can filter jobs by
### G. Zep Graphiti temporal knowledge graph [read_only_ok=True, cost=$0 self-hosted graph DB + LLM ingestion cost, effort=weeks, risk=none]
Apache-2.0 bi-temporal context graph (EntityEdge: created_at, valid_at, invalid_at, expired_at, reference_time, fact, episodes[]); hybrid vector+BM25+graph search; ingest via episodes.
Pros:
  - Best available model for facts that change over time and provenance per episode
  - Works with Anthropic/OpenAI structured-output LLMs
Cons:
  - Needs Neo4j 5.26+ or FalkorDB 1.1.2+ (Kuzu driver deprecated because upstream is unmaintained) - a graph server on Windows
  - LLM-heavy ingestion cost/latency per episode; overkill for one person's job hunt
### H. LangMem SDK (0.0.30, 2025-10-27) / Cognee / Claude memory tool as complements [read_only_ok=True, cost=$0, effort=hours, risk=none]
LangMem: memory-manager and background-extraction patterns on LangGraph BaseStore, pre-1.0 with slow releases. Cognee: local SQLite+LanceDB+Ladybug (Kuzu fork) graph-RAG, ~8 GB RAM floor. Claude `memory_20250818` tool: file-based scratchpad the model edits via `BetaAbstractMemoryTool`.
Pros:
  - Useful design references (LangMem's 'memory manager' with existing-memories-in-context update prompt; Claude memory tool for freeform agent notes)
Cons:
  - LangMem: 0.0.x, LangGraph dependency, reported high search latency
  - Cognee: heavy, graph-centric, unstable API surface
  - Claude memory tool: Claude-only (breaks GPT switchability), untyped, not reviewable like typed facts

## Concrete details
  - Verified local environment (2026-09-16): `uv run python -c` -> Python 3.12.12 [MSC v.1944], sqlite 3.50.4, enable_load_extension=True, FTS5=1, JSON=1. `uv run --with sqlite-vec --with sqlcipher3` -> sqlite-vec 'v0.1.9' loads on stdlib sqlite3 AND on sqlcipher3 (2.6.0; PRAGMA cipher_version '4.12.0 community'; compile opts include ENABLE_LOAD_EXTENSION, ENABLE_FTS5, HAS_CODEC).
  - Dependencies for v1: `uv add anthropic openai pydantic sqlite-vec keyring` ; v1.5: `uv add sentence-transformers` (or use Ollama HTTP `POST http://localhost:11434/api/embed {model:'bge-m3', input:[...]}`) or `uv add fastembed`; v2: `uv add sqlcipher3 pywin32 cryptography`.
  - Connection factory: `db = sqlite3.connect(path, isolation_level=None); db.execute('PRAGMA journal_mode=WAL'); db.execute('PRAGMA foreign_keys=ON'); db.enable_load_extension(True); import sqlite_vec; sqlite_vec.load(db); db.enable_load_extension(False)`. SQLCipher variant: `import sqlcipher3; db = sqlcipher3.connect(path); db.execute("PRAGMA key = \"x'<64 hex chars>'\"")` as the FIRST statement, then the same PRAGMAs/extension load.

  - LAYER 1 - jobs(job_id PK, company_id FK, title, title_normalized, location_text, country, city, remote_mode CHECK IN('onsite','hybrid','remote','unknown'), employment_type, seniority CHECK IN('intern','junior','mid','senior','staff','lead','manager','director','unknown'), salary_min REAL, salary_max REAL, salary_currency, salary_period CHECK IN('year','month','hour'), description_md, requirements_json, tech_tags_json, lang CHECK IN('en','ja','zh','other'), source CHECK IN('linkedin','gmail','manual','web'), source_url, source_external_id, canonical_key UNIQUE  /* sha1(company_norm|title_norm|city_norm) */, content_hash, posted_at, first_seen_at, last_seen_at, is_active BOOL, closed_at).   - LAYER 4 - vector table DDL (verified): `CREATE VIRTUAL TABLE vec_chunks_bgem3 USING vec0(chunk_id INTEGER PRIMARY KEY, embedding float[1024] distance_metric=cosine, kind TEXT PARTITION KEY, +ref_id INTEGER, +lang TEXT)`; insert with `struct.pack('1024f', *vec)` or `sqlite_vec.serialize_float32(vec)`; KNN: `SELECT chunk_id, ref_id, distance FROM vec_chunks_bgem3 WHERE embedding MATCH ? AND kind='job' AND k=50`.
  - LAYER 4 - FTS DDL (verified): `CREATE VIRTUAL TABLE fts_chunks_latin USING fts5(text, content='chunks', content_rowid='chunk_id', tokenize='unicode61 remove_diacritics 2')` and `CREATE VIRTUAL TABLE fts_chunks_cjk USING fts5(text, content='chunks', content_rowid='chunk_id', tokenize='trigram')`; maintain both with insert/delete triggers on chunks (or the FTS5 'rebuild' command). Query routing: CJK regex `[぀-ヿ㐀-鿿가-힯]` -> fts_chunks_cjk (tokens >=3 chars) else `chunks.text LIKE '%tok%'`; Latin -> fts_chunks_latin with `bm25(fts_chunks_latin)`.
  - Hybrid fusion: RRF score = sum over lists of 1/(60+rank); lists = vec KNN top-50 (filtered by kind), fts_latin top-50, fts_cjk top-50; then optional cross-encoder `BAAI/bge-reranker-v2-m3` (fastembed `TextCrossEncoder`, verify with `TextCrossEncoder.list_supported_models()`) on top-30; return top-10 chunks grouped by (kind, ref_id).
  - Extraction schema (Pydantic, closed): `class FactCandidate(BaseModel): category: Literal[...same enum...]; key: str; value_text: str; value_json: dict | None; polarity: Literal['prefer','avoid','neutral','hard_require','hard_exclude']; strength: float; confidence: float; evidence_quote: str; relation: Literal['new','confirms','updates','contradicts']; related_fact_id: int | None; valid_from: str | None; expires_in_days: int | None` ; `class ApplicationEventCandidate(BaseModel): company: str; role: str | None; event_type: Literal['applied','ack','recruiter_screen','oa','tech_interview','onsite','offer','rejection','followup_needed','scheduling','other']; event_at: str | None; confidence: float; evidence_quote: str; contact_name: str | None; contact_role: str | None; contact_email_alias: str | None` ; `class MemoryExtraction(BaseModel): facts: list[FactCandidate]; events: list[ApplicationEventCandidate]; nothing_to_extract: bool`.
  - Claude extraction call: `resp = client.messages.parse(model='claude-opus-5', max_tokens=4000, output_config={'effort':'low'}, system=[EXTRACTION_RULES, ACTIVE_FACTS_JSON, REJECTED_FACTS_JSON (cache_control on the rules block)], messages=[{'role':'user','content': turn_or_email_text}], output_format=MemoryExtraction); if resp.stop_reason=='refusal': log; else data = resp.parsed_output`. OpenAI equivalent: `resp = client.responses.parse(model=<gpt model>, input=[...], text_format=MemoryExtraction); data = resp.output_parsed`.
  - Auto-accept rule (configurable): a candidate becomes `active` without review only if source_type='user_stated' (first-person explicit statement in chat), confidence >= 0.85, relation in ('new','confirms'), and category not in ('deal_breaker','salary_expectation'); everything else waits in the inbox. Vetoed candidates keep status='rejected' and are fed back to the extractor as 'do not re-propose'.
  - Dedup/merge: exact (category,key,value_text normalized) -> 'confirms' (bump confidence: c' = 1-(1-c)(1-c_new), touch observed_at); same key different value in single-valued category -> 'updates'; opposite polarity same key/value -> 'contradicts'; fuzzy: embed `category+': '+value_text`, cosine > 0.90 within category -> flag as possible duplicate for review.
  - Expiry defaults (expires_at = observed_at + ttl): availability 14d, notice_period 90d, salary_expectation 180d (-> status stays active but UI shows 'stale, reconfirm?'), location_pref/remote_pref 365d, personality/strength/weakness/language none. Nightly job: mark expired, decay learned weights, purge `source_items.body_text` older than N days (default 90) where a derived event exists, VACUUM monthly.
  - Scoring tables: preference_weights(feature TEXT PK, w_stated REAL, w_learned REAL, n_obs INT, updated_at); job_features(job_id PK, features_json /* e.g. remote:1, salary_mid_ratio:0.9, size_match:1, tech_overlap:0.6, seniority_delta:-1, lang_match:1, commute_ok:1 */, feature_version, computed_at); job_scores(score_id PK, job_id FK, profile_snapshot_hash, hard_filter_pass BOOL, hard_filter_failures_json, soft_score REAL, llm_fit_score INT, llm_explanation, matched_criteria_json, concerns_json, model, prompt_version, scored_at, UNIQUE(job_id, profile_snapshot_hash, prompt_version)); fit_signals(job_id, application_id, signal CHECK IN('company_rejected','no_response','interview_reached','offer'), ts); search_runs(run_id PK, query_text, filters_json, ts, n_results); search_run_results(run_id FK, job_id FK, rank INT, shown BOOL).
  - Scoring pipeline: (1) SQL hard filters from active facts with polarity hard_exclude/hard_require (e.g., remote.mode, location.country, salary.base.min, visa sponsorship, company.industry avoid-list) -> record failures; (2) soft_score = sum_f (0.7*w_stated_f + 0.3*w_learned_f) * x_f with x_f in [-1,1]; (3) top-K (20-30) to LLM with `class JobJudgement(BaseModel): job_id:int; fit_score:int; matched_criteria:list[str]; concerns:list[str]; hard_filter_violations:list[str]; explanation:str` / `class RerankResult(BaseModel): judgements:list[JobJudgement]`; (4) final = 0.5*normalized soft + 0.5*llm_fit/100; persist in job_scores; (5) mark `shown` in job_interactions/search_run_results.
  - Outcome learning update (v2): label y = +1 applied, +0.5 saved, -1 dismissed, -0.25 ignored (shown >= 3 times, no action), 0 otherwise; SGD on logistic loss over job_features with lr 0.05, L2 1e-3; store into w_learned; exponential decay factor 0.5^(days/90) applied to w_learned nightly; company-side rejections update fit_signals only (used by the LLM prompt as 'realism' context, not as preference).
  - Housekeeping tables: schema_migrations(version INT PK, applied_at); audit_log(id PK, ts, actor CHECK IN('user','llm','system'), action, table_name, row_id, diff_json); pii_aliases(alias TEXT PK /* '<EMAIL_1>' */, kind CHECK IN('email','phone','url','name'), real_value, created_at) - re-hydrate LLM outputs locally by reverse lookup.
  - Privacy boundary: leaves the machine ONLY inside LLM/embedding prompts - selected chat turns, minimized job-related email text (subject + trimmed body, after a local rules classifier on sender domain/keywords marks it job_related), job posting text, the rendered profile block, retrieved chunks. NEVER leaves: OAuth tokens, Gmail headers/labels/attachments, full mailbox, resume files (unless the user explicitly asks to tailor), the SQLite file, embeddings computed locally. PII minimization: regex-replace emails/phones/URLs with aliases from pii_aliases before any API call; truncate email bodies to the first ~2,000 chars plus quoted-reply stripping.
  - Encryption-at-rest options on Windows 11 Home: (1) SQLCipher via `sqlcipher3` (AES-256, page-level; key = 32 random bytes generated once, stored as a DPAPI blob via `win32crypt.CryptProtectData(key, None, None, None, None, 0)` in %LOCALAPPDATA%\JobPilot\db.key, or in Credential Manager via `keyring.set_password('Mita JobPilot','sqlcipher_key', hex)`); (2) Windows Device Encryption (XTS-AES 128 by default) - covers the whole OS drive against offline theft, enabled automatically on clean 24H2 installs when signed in with a Microsoft account, verify via msinfo32 'Device Encryption Support: Meets prerequisites' and Settings > Privacy & security > Device encryption; registry `HKLM\SYSTEM\CurrentControlSet\Control\BitLocker\PreventDeviceEncryption` controls auto-enable; (3) field-level AES-GCM (`cryptography` package) for `source_items.body_text` and document blobs only, key in DPAPI - cheapest, keeps stdlib sqlite3. ## Open questions
  - On a Windows 11 Home machine, check whether it is signed in with a Microsoft account and whether msinfo32 reports 'Device Encryption Support: Meets prerequisites'? If not, Device Encryption is effectively off and SQLCipher/field-level encryption should move earlier in the plan.
  - How large will the corpus get (jobs + emails + notes)? Under ~100k chunks brute-force sqlite-vec is fine; beyond that plan for sqlite-vec 0.1.10 ANN (when stable) or LanceDB.
  - Which language dominates the job hunt (ja vs zh vs en)? This decides bge-m3 (balanced, best Japanese evidence) vs Qwen3-Embedding (zh/en) vs ruri-v3 (ja-only); a 50-query eval on the user's own emails/postings should be run before locking the model.
  - Does the machine have a usable GPU? bge-m3 on CPU is ~a few sentences/sec; if too slow, use multilingual-e5-base/small via fastembed ONNX or Ollama, or voyage-4-nano.
  - Is sending minimized email text to Anthropic/OpenAI acceptable to the user, and which provider retention/ZDR settings apply to their account? If not acceptable, extraction must run on a local LLM (Ollama) with lower schema fidelity.
  - voyage-4-nano's CJK retrieval quality is not benchmarked in the sources found; it is attractive for local-now/API-later but needs the same local eval.
  - Should the memory inbox auto-accept explicit first-person statements (confidence >= 0.85) or require confirmation for everything in v1? Recommendation is auto-accept for low-risk categories only.
  - Will GPT be used often enough to justify maintaining two structured-output code paths, or can extraction be pinned to one provider while only the chat model is switchable?
  - mem0 v2.0.0 release date appears as 2026-04-16 in several sources but the release page year parsed inconsistently; confirm on GitHub before citing in docs.
