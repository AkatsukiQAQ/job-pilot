# 架构提案 C：集成风险优先

> **AI 调研附录**（生成于 2026-09-16，英文）。内容由并行调研 agent 对照官方页面整理，verified/unverified 标注以原文为准；实现前需再次核对。相关更正见 japan-critique.md 与 proposal-judgments.md。

# Proposal P2 (risk): Integration-risk-first. The four things most likely to sink Mita JobPilot are external, not internal: (1) Gmail needs a Google RESTRICTED scope and its refresh tokens die every 7 days while the consent screen is in Testing; (2) LinkedIn has no readable API for an individual and its User Agreement 8.2 bans every automated alternative; (3) the read-only constraint must survive an LLM that can call tools from voice input; (4) job boards are wrapped in ToS/robots/quota rules. So the design puts a Capability Kernel (scope allowlist + single egress gate + tool registry with no external-write member) and a Source Health model in place BEFORE any feature, lands each risky integration one at a time behind one ReadOnlySource port with a proven fallback ladder (API -> official export -> user-owned email -> manual/voice entry), and treats "this source is down/stale" as a first-class UI state rather than an error. Every phase is independently useful, and the memory <-> search learning loop is placed late but its ledgers (job_interactions, application outcomes, provenance) are written from day one so the loop has data when it arrives.
Mita JobPilot is a single-user, local-first Windows workbench (Python 3.12 + uv, FastAPI + SQLite, React UI from phase 2) that ingests job-hunt signals strictly read-only (Gmail/Calendar read scopes, LinkedIn data archive + LinkedIn notification mail, public ATS/job-board endpoints), keeps a provenance-stamped application tracker plus a bi-temporal memory of the user's profile, preferences and outcomes, and exposes both to a switchable Claude/GPT chat (MCP hosts first, in-app pydantic-ai later) where voice or text can operate the app only through propose -> confirm, and can never write to the outside world because no code path for external writes exists.

## Architecture components
- Capability Kernel (jobpilot/policy): The only place that can mint outbound clients. Capability enum {READ_GMAIL, READ_CALENDAR, READ_PUBLIC_HTTP, LLM_INFERENCE, LOCAL_DB_WRITE} has no external-write member. scopes.py holds ALLOWED_OAUTH_SCOPES = {gmail.readonly, calendar.events.readonly} and asserts token scopes are a subset at startup (via creds.scopes and GET oauth2.googleapis.com/tokeninfo). egress.py builds every httpx client with a request event hook that denies any method other than GET/HEAD unless (host, path) is in an explicit POST allowlist (oauth2.googleapis.com/token for refresh, api.anthropic.com/v1/messages, api.openai.com/v1/responses and /v1/audio/transcriptions, later stateless search POSTs such as *.jooble.org/api/*), and denies FORBIDDEN_HOSTS (linkedin.com, indeed.com, glassdoor.com, wantedly.com, bizreach.jp, green-japan.com, doda.jp) outright. google_http.py wraps google_auth_httplib2.AuthorizedHttp in ReadOnlyHttp whose request() raises EgressDenied for non-GET except the gmail batch envelope. Every outbound request is appended to egress_log so `jobpilot egress-report` can prove 0 write requests. [httpx event_hooks, google-auth-httplib2 wrapper, pytest + ast source scan (tests/test_policy.py)]
- Secrets store (jobpilot/secrets): SecretStore Protocol with WindowsSecretStore (keyring 25.7 / Credential Manager for short API keys and the optional IMAP App Password; DPAPI-encrypted file via win32crypt.CryptProtectData for the Google token JSON because CredWrite fails on blobs around 700+ chars) and EnvSecretStore for tests. A secret-name allowlist means no slot exists for a LinkedIn cookie, SMTP password or w_member_social token. [keyring 25.7.0, pywin32 312 (win32crypt), pydantic-settings]
- Connectors (jobpilot/connectors): Adapters implementing ReadOnlySource Protocol: probe() -> SourceHealth, backfill(cursor) -> Iterator[RawItem], poll(cursor) -> (Iterator[RawItem], new_cursor). Connectors receive their client from the kernel (dependency injection), never open sockets themselves, never receive a DB session, and only return frozen RawItem records. Adapters: gmail_api (primary), gmail_imap (fallback, EXAMINE + BODY.PEEK only), gcal, linkedin_archive (ZIP importer), linkedin_mail (template parser over Gmail items), ats_boards (Greenhouse/Lever/Ashby/SmartRecruiters/Workable/Recruitee/Teamtailor/Rippling), aggregators (Adzuna, JSearch), remote_boards (Remotive/Himalayas/Jobicy/Arbeitnow/RemoteOK/The Muse), tokyo_boards (TokyoDev/Japan Dev sitemap + JSON-LD), gmail_alerts (LinkedIn/Indeed/Wantedly/Bizreach/Green/doda alert mail), mbox_import (Takeout, one-time). [google-api-python-client 2.200 (static_discovery=True, cache_discovery=False), google-auth-oauthlib 1.4.1 InstalledAppFlow, stdlib imaplib/zipfile/csv/mailbox, httpx, feedparser, extruct, protego]
- Sync orchestrator + scheduler (jobpilot/services/sync): Runs each connector on its cadence (gmail history.list every 90 s, calendar syncToken every 120 s, ATS boards every 4 h, aggregators daily within quota, archive folder watch on change), owns per-source cursor and token buckets (source_quota), applies exponential backoff, and writes source_state {healthy, degraded, auth_required, unavailable, disabled} with last_success_at/next_retry_at/staleness. Publishes sync.progress / source.state events to the in-process broadcaster. Same job functions are callable once from the CLI (`jobpilot sync gmail`). [APScheduler 3.11.3 AsyncIOScheduler in FastAPI lifespan; asyncio.to_thread for the blocking Google client; watchdog for the Downloads folder]
- Ingestion pipeline (jobpilot/services/ingest): normalize (RawItem -> email_message / calendar_event / job_posting rows, idempotent on natural keys) -> classify stage 1 (deterministic sender-domain + subject regex table with rule_id, covers ATS templates, LinkedIn statuses, job-alert digests to discard, calendar notices) -> classify stage 2 (only gated/ambiguous mail; PII-aliased, truncated text to Claude/GPT with a closed Pydantic schema; cached in llm_cache by input hash) -> link (thread, company domain, li_job_id, ATS job id, calendar attendee domain) -> write application_event with user_confirmed=0 and before/after diff in audit_log. Manual status always beats auto: auto never downgrades a manually set status; conflicts go to the review inbox. [pydantic v2 models, rapidfuzz, pydantic-ai structured output (Claude messages.parse / OpenAI responses.parse underneath)]
- Tracker service (jobpilot/services/pipeline): Applications, application_events, interview_slots (state pending_schedule vs confirmed, JST rendering, 'meeting link unconfirmed' when no URL), contacts (local-only PII), user_notes, exclusion records with reason. Every mutation goes through one function that writes audit_log(before, after, actor, source). [SQLAlchemy 2.0.54 typed declarative, Alembic 1.20 (render_as_batch=True), FTS5]
- Job search service (jobpilot/services/search): watch_target polling via connectors, NFKC/company-suffix normalization, canonical_key + rapidfuzz + MinHash dedup, listing_status {confirmed_open, unverified, lead, excluded}, hiring_track {new_grad_2027, mid_career, intern}, job_interactions ledger (shown/ignored/saved/dismissed/applied), never-reshow filter, hard filters + weighted soft score from profile_facts, LLM rerank of top-K with stored explanations. This module is where the memory -> search half of the loop lives. [rapidfuzz, datasketch MinHash, SQL, pydantic-ai structured output for RerankResult]
- Memory service (jobpilot/services/memory): profile_facts with bi-temporal supersession, extraction_runs after chat turns and job emails, memory inbox (candidate -> active/rejected), rendering of active facts into a cached system-prompt block, FTS5 retrieval (unicode61 + trigram dual tables, LIKE fallback for 1-2 char CJK), later sqlite-vec hybrid retrieval, nightly learn job that turns job_interactions and application outcomes into preference_weights.w_learned and fit_signals. This is the outcomes -> memory half of the loop. [SQLite FTS5, sqlite-vec 0.1.9 (phase 6), sentence-transformers bge-m3 or Ollama (phase 6), pydantic-ai structured output]
- Agent layer (jobpilot/agent): One static tool registry (tools/readonly.py, tools/local_mutations.py) where each tool declares side_effect in {none, local_db}; tools import only jobpilot.services, never jobpilot.connectors. Mutations are two-phase: propose_*() writes pending_actions and returns {action_id, summary, diff}; confirm_action(action_id) is invoked by application code after a UI click, an MCP host approval, or a deterministic keyword match on a voice transcript, never by the model itself. Phase 3 exposes the registry as an MCP stdio server (jobpilot-mcp) for Claude Desktop / Claude Code / Codex; phase 5 wraps the same functions in a pydantic-ai FunctionToolset with requires_approval=True for the in-app chat with provider switch by model string. [mcp 2.2.0 (FastMCP, stdio), pydantic-ai-slim[anthropic,openai,mcp] 2.43.0, model ids from settings (anthropic:claude-opus-5 default, anthropic:claude-haiku-4-5 bulk, openai:gpt-5.6-terra alternate, openai:gpt-5.6-luna bulk)]
- API + realtime (jobpilot/api): Routers: /api/applications, /api/jobs, /api/emails, /api/interviews, /api/imports/linkedin, /api/sync, /api/sources, /api/memory, /api/pending-actions, /api/chat (SSE token stream), /api/events (SSE: source.state, application.updated, email.new, interview.updated, ui.command), /api/voice/transcribe, /api/settings/llm. No GZip middleware (breaks SSE). [FastAPI 0.141.1, uvicorn on 127.0.0.1:8765, sse-starlette 3.4.11]
- Web UI (frontend/): Pages: Today (summary, upcoming interviews, pending confirmations, source health strip with 'as of' times), Pipeline (board + table), Application detail (timeline of emails/events, manual override, notes), Interviews (JST month overview + agenda; confirmed vs pending separated), Opportunities (filters/sort per product reference, cards, compare up to 3), Sources (per-source status, quotas, reconnect buttons), Memory inbox (confirm/edit/veto facts), Chat (provider dropdown, streaming, confirm cards, push-to-talk). Fallback if React slows you down: NiceGUI 3.16 mounted via ui.run_with(app) on the same FastAPI app. [React 19 + TypeScript + Vite 8, TanStack Query 5, Tailwind 4, EventSource, Web Speech API]
- Voice (frontend/src/voice + jobpilot/api/voice.py): Push-to-talk only. Browser SpeechRecognition (lang toggle ja-JP / zh-CN / en-US, interimResults) fills the chat input and shows the transcript before submit; fallback MediaRecorder clip -> POST /api/voice/transcribe -> OpenAI gpt-transcribe (keywords seeded with company names) or local faster-whisper. Voice commands become ordinary chat messages so they hit the same tool registry and the same propose/confirm gate. [Web Speech API (Chrome/Edge), Windows Win+H dictation (zero code), openai 3.14 audio.transcriptions, optional faster-whisper 1.2.1]
- Storage (jobpilot/db): Single SQLite file at %LOCALAPPDATA%/Mita JobPilot/jobpilot.db (override JOBPILOT_HOME), WAL, busy_timeout=5000, foreign_keys=ON, check_same_thread=False; Alembic migrations with MetaData naming_convention and render_as_batch; FTS5 external-content tables with triggers; vec0 tables from phase 6; connection factory abstracted so sqlite3 -> sqlcipher3 is a one-function swap in phase 7. [SQLite 3.50.4 (uv CPython 3.12.12, FTS5 + load_extension verified), SQLAlchemy 2.0.54, Alembic 1.20, platformdirs]
- CLI (jobpilot/cli.py): `jobpilot doctor` (runtime, data dir, secrets backend, token scopes, egress self-test), `auth google`, `sync gmail|calendar|boards [--backfill]`, `watch` (scheduler loop without UI), `senders` (discover job-related senders/subject templates in your own inbox), `pipeline`, `import linkedin <zip>`, `egress-report`, `mcp` (stdio server), `serve`, `dev`, `db upgrade`. [typer, rich]

## Data flow
Ingest: scheduler tick -> kernel.grant(READ_GMAIL) returns a ReadOnlyHttp-wrapped Gmail service -> connectors.gmail_api.poll(cursor=history_id) issues GET users.history.list / messages.get (metadata for all, full only for gated mail) -> frozen RawItem rows land in raw_item (immutable, UNIQUE(source, external_id)) and every request lands in egress_log -> ingest.normalize writes email_message -> classify stage 1 (rules table, rule_id) -> stage 2 only for gated/ambiguous items: PII-aliased, truncated text -> Claude/GPT structured output -> email_classification (+ llm_cache) -> link to company/application by thread id, ATS job id, li_job_id, sender domain -> application (auto-created from confirmations with status_source=auto) and application_event(user_confirmed=0) -> audit_log(before/after) -> broadcaster emits application.updated over /api/events -> UI badge 'auto-detected, confirm?'. Calendar events follow the same path via connectors.gcal (events.list syncToken) into calendar_event -> interview_slot(state=confirmed) joined by attendee/organizer domain and keywords; scheduling requests found in mail create interview_slot(state=pending_schedule). LinkedIn: Downloads watcher or `import linkedin` -> source_import -> Jobs/*.csv, messages.csv upserted by natural keys -> applications (channel=linkedin_easy_apply) and li_message; LinkedIn notification mail from the Gmail path links to the same application via li_job_id. Chat: user text or voice transcript -> agent (MCP host in phase 3, pydantic-ai in phase 5) -> read tools query services (bounded, ids cited) -> mutation intent -> propose_* writes pending_actions and returns summary/diff -> host approval / UI confirm card / deterministic 'confirm' keyword -> application code calls confirm_action -> services -> audit_log -> event. Search loop: watch_target poll -> job_posting (source, source_id) -> dedup into job_canonical -> job_features -> SQL hard filters from active profile_facts with polarity hard_require/hard_exclude -> soft score with 0.7*w_stated + 0.3*w_learned -> LLM rerank top-K -> shown rows written to job_interactions -> user saves/dismisses/applies -> outcomes arrive from Gmail classifier as application_events -> nightly learn job updates preference_weights.w_learned and fit_signals -> next search ranks differently. Memory loop: every chat turn and job-related email -> extraction_run -> profile_facts(status=candidate) -> inbox -> active (supersedes old fact bi-temporally) -> rendered profile block in the next system prompt and the next search's hard filters.

## Data model
- source_state: source TEXT PK (gmail, gcal, linkedin_archive, linkedin_mail, ats:<board>, adzuna, jsearch, remotive, ..., manual), transport TEXT (api|imap|archive|email|http), status TEXT CHECK IN (healthy, degraded, auth_required, unavailable, disabled), cursor TEXT (Gmail historyId / Calendar syncToken / archive sha256 / etag), last_success_at, last_error, failure_streak INT, next_retry_at, data_as_of
  Drives the Sources strip and every 'as of' label. auth_required renders a one-click reconnect; disabled is the user kill-switch. Nothing is deleted when a source dies.
- source_quota: source TEXT PK, capacity INT, refill_per_sec REAL, daily_cap INT, monthly_cap INT, used_today INT, used_month INT, reset_at
  Token buckets encoding official limits: Adzuna 25/min + 250/day + 2500/month, JSearch 200/month, Remotive 4/day, Jobicy 1/hour, Gmail 6000 units/min. Exhaustion flips source_state to unavailable until reset, never to an error.
- egress_log: id PK, ts, capability, method, host, path, status_code, allowed BOOL, denied_reason
  Written by the kernel hook for every outbound request. `jobpilot egress-report` asserts count(method NOT IN (GET, HEAD) AND host NOT IN allowlist) == 0.
- raw_item: id PK, source, external_id, thread_key, fetched_at, payload_json, content_hash, UNIQUE(source, external_id)
  Immutable landing zone. Re-processing after a rules/prompt change replays from here without touching any external service. body payload purgeable after N days once derived rows exist.
- email_message: gmail_id TEXT PK, thread_id, history_id INT, internal_date_ms, message_id_hdr UNIQUE, in_reply_to, from_addr, from_domain, reply_to, to_addr, subject, snippet, label_ids JSON, has_attachments, body_text (trimmed, purgeable), auth_results (DKIM/SPF), transport (api|imap|mbox)
  Transport-agnostic: IMAP fallback maps X-GM-MSGID to gmail_id and Message-ID header is the cross-transport dedup key.
- email_classification: gmail_id PK FK, is_job_related, category CHECK IN (confirmation, viewed, rejection, interview_invite, scheduling_request, assessment, offer, outreach, job_alert, calendar_notice, system, other), company, role, ats, stage, action_required, deadline_iso, event_start_iso, links JSON, language, confidence, method (rule|llm|user), rule_id, model, prompt_version, classified_at, user_override_category
  user_override wins forever; llm rows cached so nothing is re-sent to a provider.
- calendar_event: event_id TEXT PK, ical_uid, status, summary, start_iso, end_iso, organizer_email, attendees JSON, conference_uri, conference_solution, html_link, updated_iso, is_interview, application_id FK NULL
  From calendar.events.readonly syncToken sync; 410 GONE triggers full resync. Also populated from .ics attachments if the Calendar API is unavailable.
- company: company_id PK, name, name_normalized UNIQUE, domain, industry, size_bucket, hq_location, is_startup, notes
  Normalization: NFKC, casefold, strip legal suffixes (Inc, K.K., 株式会社, 合同会社, (株)).
- job_posting: id PK, canonical_id FK, source, source_id, UNIQUE(source, source_id), source_url, apply_url, company_id FK, title, title_norm, location_raw, city, country_code, remote_type, employment_type, hiring_track CHECK IN (new_grad_2027, mid_career, intern, unknown), requires_internship_first BOOL, listing_status CHECK IN (confirmed_open, unverified, lead, excluded), excluded_reason, verified_at, application_deadline, salary_min/max/currency/period, description_text, language, posted_at, first_seen_at, last_seen_at, is_active, content_hash, attribution_text, raw JSON
  Job facts only; judgments live in job_score/user_note, status in application, schedule in interview_slot (separation demanded by the product reference).
- job_canonical: id PK, blocking_key sha1(company_norm|title_norm|country|city_or_remote), best_posting_id, source_count, status (open|closed), first_seen_at, last_seen_at
  Merge when token_set_ratio(title) >= 90 and MinHash Jaccard >= 0.7; ATS-direct posting wins as best_posting_id.
- watch_target: id PK, kind (ats:<vendor>|sitemap|rss|aggregator_query), company_name, identifier (board token / subdomain / URL / query JSON), poll_interval_min, last_polled_at, etag, last_modified, enabled, robots_ok BOOL, robots_checked_at
  ATS auto-detector fills kind+identifier from a pasted careers URL.
- application: application_id PK, job_posting_id FK NULL, company_id FK, role_title, status CHECK IN (considering, preparing, applied, assessment, interviewing, offer, accepted, rejected, withdrawn, unfit, ghosted), status_source CHECK IN (manual, auto), status_set_at, channel CHECK IN (linkedin_easy_apply, company_ats, referral, recruiter, email, manual), external_ref (ATS job id / li_job_id), applied_at, last_activity_at, current_situation, next_action, next_action_due, outcome, outcome_at, outcome_reason, source_import_id FK NULL
  Rule: an auto update never overwrites status_source=manual; it creates a pending review event instead.
- application_event: event_id PK, application_id FK, event_type CHECK IN (applied, ack, viewed, recruiter_screen, assessment, interview, onsite, offer, rejection, scheduling, followup_needed, note, status_change, archive_import), occurred_at, detected_from CHECK IN (email, calendar, linkedin_archive, linkedin_mail, chat, voice, manual), source_ref (gmail_id | event_id | import row | chat_turn_id), confidence, summary, before_json, after_json, user_confirmed BOOL, UNIQUE(application_id, event_type, occurred_at, source_ref)
  Idempotent ingestion; every auto update is auditable with before/after, source and confirmation state.
- interview_slot: slot_id PK, application_id FK, state CHECK IN (pending_schedule, confirmed, done, cancelled), round_label, start_at_utc NULL, end_at_utc NULL, mode (online|onsite|phone|unknown), tool_or_location, meeting_url NULL, meeting_url_status (present|unconfirmed|not_applicable), calendar_event_id FK NULL, source_email_id FK NULL, notes
  UI separates pending_schedule from confirmed; displays in Asia/Tokyo; shows 'meeting link unconfirmed' when meeting_url is NULL, never fabricates one.
- contact: contact_id PK, company_id FK, name, role, email, linkedin_url, relationship (recruiter|hiring_manager|interviewer|referral|agency), first/last_contact_at
  Local-only PII; excluded from prompts (replaced by pii_aliases) and from any UI list view.
- source_import: id PK, source (linkedin_export|mbox), archive_type (basic|complete), zip_name, sha256 UNIQUE, archive_date, imported_at, files_json (name -> header row -> row count)
  Provenance for every archive-derived row; UI shows 'LinkedIn data as of <archive_date>'.
- li_message / li_saved_job / li_job_seeker_preferences / li_saved_job_alert: li_message PK (conversation_id, date_utc, sender_profile_url); subject, content, folder, is_draft, li_saved_job (li_job_id, saved_date, title, company, url), li_job_seeker_preferences single-row snapshot per import (locations, industries, job_titles, dream_companies, introduction_statement), li_saved_job_alert (saved_search_id, alert_parameters, query_context)
  Headers matched dynamically by normalized file stem; preferences and alerts seed profile_facts (source_type=linkedin_profile_csv) and 'previously searched' context.
- job_interaction: id PK, job_posting_id FK, action CHECK IN (shown, ignored, saved, dismissed, applied, withdrawn, compared), reason_text, search_run_id FK NULL, ts
  Never-reshow rule reads this; also the training signal for w_learned.
- search_run / search_run_result: search_run(run_id PK, query_text, filters_json, sources_json, profile_snapshot_hash, ts, n_results), search_run_result(run_id, job_posting_id, rank, soft_score, llm_fit_score, shown BOOL)
  Requirement 4's 'previous searches'; UI can replay a run.
- profile_fact: fact_id PK, category CHECK IN (role_target, seniority_target, salary_expectation, location_pref, remote_pref, company_type_pref, company_size_pref, industry_pref, tech_pref, culture_pref, work_style, deal_breaker, personality, strength, weakness, language, visa_status, availability, graduation, notice_period, other), key (dotted slug e.g. salary.base.min_jpy), value_text, value_json, polarity CHECK IN (prefer, avoid, neutral, hard_require, hard_exclude), strength 0..1, confidence 0..1, source_type CHECK IN (user_stated, user_confirmed, llm_inferred, outcome_inferred, linkedin_profile_csv, manual), source_ref, evidence_quote, lang, valid_from, valid_to NULL, expires_at NULL, status CHECK IN (candidate, active, superseded, rejected, expired), superseded_by FK NULL, extraction_run_id FK
  Bi-temporal (Graphiti-style). Partial unique index on key WHERE status=active for single-valued categories.
- extraction_run / llm_cache: extraction_run(run_id PK, source_type (chat_turn|email|linkedin|summary), source_ref, provider, model, prompt_version, schema_version, input_hash, output_json, n_candidates, status, tokens, cost_usd, UNIQUE(source_type, source_ref, prompt_version, schema_version)), llm_cache(input_hash PK, task, model, output_json, created_at)
  Guarantees nothing is classified or extracted twice for the same input+prompt version.
- chat_session / chat_turn / episode_summary: chat_session(session_id PK, started_at, provider, model, title), chat_turn(turn_id PK, session_id FK, idx, role, content, content_json (tool calls), modality (text|voice), asr_confidence, tokens, extracted_at, UNIQUE(session_id, idx)), episode_summary(summary_id PK, session_id FK NULL, turn_start, turn_end, summary_md, key_facts_json, open_loops_json, model, prompt_version)
  History is provider-neutral so a session can switch Claude <-> GPT mid-way.

## Memory design
Four layers in the one SQLite file, all local, all provenance-stamped, with a review gate between what the model infers and what the app believes.

LAYER 1 - structured history (from phase 1): companies, job_postings, applications, application_events, interview_slots, job_interactions, search_runs, fit_signals. This is the "positions applied to and their outcomes" memory and it is written by the ingestion pipeline and the UI from day one, so the learning loop has data before the loop exists.

LAYER 2 - typed profile facts (phase 5): profile_fact rows with category (role_target, salary_expectation, location_pref, remote_pref, company_type_pref, company_size_pref, industry_pref, tech_pref, culture_pref, work_style, deal_breaker, personality, strength, weakness, language, visa_status, availability, graduation, ...), dotted key, value_text/value_json, polarity (prefer/avoid/neutral/hard_require/hard_exclude), strength, confidence, source_type (user_stated, user_confirmed, llm_inferred, outcome_inferred, linkedin_profile_csv, manual), evidence_quote, and bi-temporal fields valid_from/valid_to/expires_at plus status candidate/active/superseded/rejected/expired and superseded_by (Graphiti-style edge invalidation). Single-valued categories carry a partial unique index on key WHERE status=active. Seeds: LinkedIn Profile/Positions/Skills/Job Seeker Preferences CSVs and a short onboarding form (graduation 2027, target roles ARE/FDE/MLE/SWE/AI product, Tokyo, salary band, industries not limited to AI companies).

LAYER 3 - conversational memory (phase 5/6): chat_session, chat_turn (provider-neutral content_json, modality text|voice, asr_confidence), episode_summary (summary_md, key_facts_json, open_loops_json every 40 turns or on session end, weekly rollup). The system prompt is: static rules -> rendered active profile block (cache_control breakpoint) -> last N episode summaries -> retrieved chunks -> current turn.

LAYER 4 - retrieval index (FTS5 in phase 5, sqlite-vec in phase 6): chunks(kind, ref_id, chunk_idx, text, lang) with fts_chunks_latin (unicode61) and fts_chunks_cjk (trigram; LIKE fallback for 1-2 character CJK queries), then vec_chunks_bgem3 USING vec0(embedding float[1024] distance_metric=cosine, kind PARTITION KEY) with local bge-m3 embeddings; hybrid RRF over the three lists; embedding_index records model_name/dims so a model change is a new table, not a silent mismatch.

EXTRACTION PIPELINE: after every user chat turn (text or voice) and every email classified job_related, services/memory/extract.py runs one structured-output call (MemoryExtraction with FactCandidate[] and ApplicationEventCandidate[]) that receives the current active facts and previously rejected facts, so it returns relation new/confirms/updates/contradicts with related_fact_id and an evidence quote. Candidates land in the memory inbox (status=candidate). Auto-accept only when source_type=user_stated, confidence >= 0.85, relation in (new, confirms) and category not in (deal_breaker, salary_expectation); everything else waits for confirm/edit/veto. Confirming updates/contradicts runs the supersession transaction (old.valid_to=now, status=superseded, superseded_by=new; new.status=active, source_type=user_confirmed). Vetoed candidates stay rejected and are fed back as do-not-re-propose. Voice turns with asr_confidence < 0.8 force review for every fact. Dedup: exact (category,key,value) -> confirms and confidence bump; same key/different value in a single-valued category -> updates; opposite polarity -> contradicts; fuzzy duplicates flagged via cosine > 0.9 within a category in phase 6. Expiry: availability 14 d, notice_period 90 d, salary_expectation 180 d (stays active, UI shows stale/reconfirm), location/remote 365 d, personality/strength/language never; nightly job marks expired and purges raw source_items.body_text older than 90 days where derived events exist.

WHERE THE LEARNING LOOP LIVES: services/search/rank.py consumes memory (hard_require/hard_exclude facts -> SQL WHERE; stated weights -> soft score; fit_signals -> realism context in the rerank prompt), while services/memory/learn.py (nightly, phase 6) produces memory from outcomes: job_interactions (applied +1, saved +0.5, dismissed -1, ignored 3x -0.25) train preference_weight.w_learned by SGD on job_features with 90-day half-life decay, blended 0.7*w_stated + 0.3*w_learned; application outcomes from the Gmail classifier become fit_signal rows (company_rejected, no_response, interview_reached, offer) and outcome_inferred fact candidates ("companies of size 5000+ have not responded in 8/8 cases") that still go through the inbox. Every job_score stores profile_snapshot_hash, model and prompt_version so scores are reproducible and re-scoring is skipped when nothing changed. A Weights page shows stated vs learned so the loop is inspectable and correctable, never silent.

PRIVACY BOUNDARY: what leaves the machine is only the text inside LLM/embedding prompts (selected chat turns, minimized job-related email text after quote stripping and truncation, job posting text, the rendered profile block, retrieved chunks), with emails/phones/URLs/names replaced by pii_alias tokens and re-hydrated locally. OAuth tokens, headers, labels, attachments, contacts, resume files, the DB and locally computed embeddings never leave. Encryption-at-rest: Windows Device Encryption now, SQLCipher via the connection-factory swap in phase 7. The memory system holds only Gmail ids, LinkedIn URLs and hashes as provenance; it never writes back to any external service.

## Read-only guarantee
The guarantee is layered so that removing any one layer still leaves the others; none of them is "the prompt says don't".

1. Credentials that cannot write. Google tokens are minted with exactly gmail.readonly and calendar.events.readonly; scopes.py asserts creds.scopes and the live tokeninfo response are a subset of ALLOWED_OAUTH_SCOPES at every startup and deletes the token otherwise, so Google's servers reject any write (messages.send/modify/trash/delete, drafts, labels, calendar insert/patch) with 403 insufficient scope even if code tried. The IMAP fallback uses an App Password (no OAuth write scope), and mail.google.com, gmail.modify/send/compose/insert/labels, calendar, calendar.events and w_member_social are string-banned in the repo. The secrets store has a name allowlist, so there is no slot for a LinkedIn cookie, an SMTP password or a write token.

2. One egress gate. jobpilot/policy/egress.py is the only module allowed to construct an HTTP client (test_policy AST-scans src/ for httpx.Client/AsyncClient, requests, urllib.request, aiohttp, smtplib, imaplib outside gmail_imap.py). Every httpx client carries a request hook that denies any method other than GET/HEAD unless (host, path) is in an explicit POST allowlist (oauth2.googleapis.com/token for refresh, api.anthropic.com/v1/messages, api.openai.com/v1/responses and /v1/audio/transcriptions, later stateless job-search POSTs per host pattern) and denies FORBIDDEN_HOSTS (linkedin.com, indeed.com, glassdoor.com, wantedly.com, bizreach.jp, green-japan.com, doda.jp) outright. The Google API client is built with http=ReadOnlyHttp(AuthorizedHttp(creds)) whose request() raises for non-GET (batch envelope excepted), so even the library cannot call a write method. gmail_imap.py exposes only examine/search_raw/fetch_peek on a private IMAP4_SSL; STORE/COPY/APPEND/EXPUNGE/SELECT are never surfaced and are string-banned in that module. Every outbound request is written to egress_log; `jobpilot egress-report` and the Sources page show the count of non-allowlisted writes, which must be 0.

3. Connectors are pure readers. ReadOnlySource Protocol has only probe/backfill/poll returning frozen RawItem records; connectors receive their client from kernel.grant(Capability) and the Capability enum has no external-write member (asserted by test); connectors never receive a DB session and expose no symbol starting with send/post/apply/label/delete/message/write (asserted by test).

4. The LLM cannot reach connectors. Tools live in jobpilot/agent/tools and import only jobpilot/services (local DB); test_policy fails if a tool module imports jobpilot.connectors or any HTTP library. The registry is a static allowlist with side_effect in {none, local_db}; MCP tools/list is generated from it in deterministic order and the same list backs pydantic-ai, so voice, MCP hosts and the in-app chat all see the identical, write-free surface.

5. Local mutations are two-phase and human-confirmed. propose_* tools write pending_actions (10-minute expiry) and return a summary/diff; confirm_action is executed by application code after a UI click, an MCP host approval prompt, or a deterministic keyword regex on a voice transcript - never by the model calling confirm itself (pydantic-ai requires_approval=True -> DeferredToolRequests; the MCP server refuses confirm_action calls whose action_id was not surfaced to the host in the same session). Auto-detected changes from sync are written with user_confirmed=0 and never overwrite a manual status; every change is in audit_log with before/after, actor and source.

6. LinkedIn by construction. No module, dependency or secret exists for authenticated LinkedIn access; the archive importer reads a ZIP the user downloaded; the mail parser reads Gmail items; the optional public-page GET is off by default and limited to one path pattern with no cookies.

7. Verification you can run. tests/test_policy.py in CI/pre-commit; scripts/prove_readonly.py prints the live token scopes; `jobpilot egress-report` proves zero writes over the log; docs/adr/0001 records the design so a future change to any allowlist is a deliberate, reviewed edit.

## Top risks
- Gmail refresh token dies every 7 days (External + Testing) and sync silently stops -> Publish the consent screen to In production without verification (allowed for personal use), re-consent after publishing so the new token is off the 7-day clock, assert token health at startup and on every 401/invalid_grant, surface auth_required with a one-click reconnect, and keep the IMAP App Password transport ready behind the same ReadOnlySource port. Verify with an 8-day soak in phase 1.
- Google tightens access to restricted scopes for unverified apps, or the OAuth client is invalidated -> Transport independence: email_message is keyed by Message-ID header and the classifier works on normalized rows, so gmail_transport=imap (EXAMINE + BODY.PEEK, X-GM-RAW) or a Takeout MBOX import replaces the API with no downstream change; the app degrades to archive + manual, never to unusable.
- LinkedIn has no API and any automation risks account restriction during an active job hunt -> Only the official data archive, LinkedIn's own notification emails and manual/voice logging are used; linkedin.com is in FORBIDDEN_HOSTS, li_at/JSESSIONID/voyager/playwright are banned symbols in CI, and the ToS/legal record (UA 8.2, hiQ, Proxycurl, ProAPIs) is written into the README so the decision is not relitigated later.
- Misclassified emails (Japanese pass/fail mails share the subject 選考結果のご連絡; scheduling request vs confirmed interview) corrupt the pipeline -> Two-stage classification with rule_id provenance, LLM structured output with evidence quotes and confidence, review inbox below 0.7, auto never overwrites manual status, corrections cached so they are never re-proposed, pending_schedule kept separate from confirmed and no meeting link ever fabricated.
- The LLM or a voice misrecognition triggers an unintended operation, or the assistant claims it did something externally -> No write tools exist; local mutations are propose -> pending_actions -> human confirm (UI click, host approval, or deterministic keyword outside the model); transcript is shown before send; grounding prompt forbids claiming actions; audit_log records actor and source for every change.
- Job-source ToS/quota violations (Adzuna 250/day, JSearch 200/month, Remotive 4/day, robots.txt, attribution) -> source_quota token buckets encode official caps and flip a source to unavailable rather than erroring; protego robots check before any new host; attribution_text stored per source and rendered; Japanese boards and LinkedIn/Indeed consumed only via alert emails; per-source kill-switch.
- Private data (recruiter PII, email bodies, resume) leaks to LLM providers -> pii_alias replacement and body minimization before any API call; contacts, tokens, headers, attachments and the DB never leave; local embeddings by default; Device Encryption now and SQLCipher via the connection-factory swap later.
- Solo evening/weekend developer burns out on scope (React toolchain, memory system, voice) before anything is useful -> Phase 1 is CLI-only and already tracks real applications; chat and voice arrive in phase 3 via MCP hosts with zero UI code; NiceGUI on the same FastAPI app is the documented fallback if React stalls; every phase has a concrete exit test and ships independently.
- SQLite contention between the API threadpool, the scheduler and imports -> WAL, busy_timeout=5000, check_same_thread=False, short write transactions, single-process design with no job queue, and immutable raw_item landing so re-processing never re-fetches.
- Model ids, SDK shapes and provider policies drift (Claude Fable 5.1 rejects forced tool_choice, anthropic 1.x uses httpx2, OpenAI Assistants API sunset) -> Model strings and pricing live in settings, pydantic-ai isolates SDK differences, structured outputs use provider-native parse methods, and the digest URLs are recorded in docs/adr for re-verification at each phase start.
- Windows-specific traps: Credential Manager blob size limit, uv 0.10 lacking uv_build defaults, browser mic requiring a secure context -> DPAPI file for the Google token with pywintypes.error caught (no plaintext fallback), `uv self update` in phase 0, UI served only on http://127.0.0.1 which counts as a secure context.
